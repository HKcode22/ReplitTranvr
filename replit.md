# Travnr - Personal Travel Concierge Platform

## Overview
Travnr is a full-stack web application designed as the central hub for a personal travel concierge service. It enables users to create accounts, manage traveler profiles, request concierge calls, receive and approve travel itinerary proposals with detailed pricing, view a travel calendar, manage notifications, and handle billing and payments. The platform automates aspects of the concierge service, from voice AI interactions to flight bookings, aiming to streamline travel planning and management for both users and administrators.

## System Architecture

Travnr utilizes a modern full-stack architecture. The frontend is built with **React 18, TypeScript, Vite, Tailwind CSS, and shadcn/ui**, ensuring a responsive and visually appealing user interface. UI/UX design emphasizes a clean, intuitive experience with dark/light mode support.

The backend operates on **Express.js with TypeScript**, providing a robust API layer. Data persistence is managed by **PostgreSQL** through **Drizzle ORM**. Authentication is custom, using email/password with `bcrypt` for hashing and `express-session` for session management.

Key features and their technical implementations include:

-   **Authentication:** Custom email/password system with SendGrid for email verification, and a comprehensive forgot/reset password flow.
-   **Traveler Profiles:** Users can manage detailed traveler profiles including passport information.
-   **Concierge Call Requests:** Users can initiate call requests, which are automatically dispatched to **Bland AI** for voice-driven concierge interactions. Bland AI integration includes dynamic data lookup for personalized conversations, call transcripts, and recordings. The dynamic-data endpoint also returns a `previous_proposal_info` field that surfaces a returning caller's most recent unbooked guest proposal (looked up via phone↔email map, 24h window) so the AI can offer to revisit prior options instead of starting fresh. For inbound calls where `call_id` doesn't resolve to a Travnr user, `/api/bland/dynamic-data` also resolves the caller to their Travnr account by phone (sources, in priority order: `traveler_profiles.phone`, prior `bland_calls.phone_number`, and `phone_email_map.email → users.email`) so returning customers get full profile/email/booking/proposal context without spelling their email out loud. Structured trip details (origin/destination IATA codes, dates, passengers, cabin class, budget, email) are extracted post-call via Bland's `analysis_schema` (a separate LLM pass over the transcript that the live agent never reads), so the caller never hears JSON, field names, or the word "null" at end of call. The webhook stashes that analysis under `bland_calls.variables.__analysis` so re-trigger paths (manual regenerate, Claude verifier loop) can recover it; `parseTravelDetailsFromTranscript` consumes it as the highest-priority source, falling back to the legacy `<TRAVEL_DETAILS>` block (for in-flight calls dispatched before this change) and then regex heuristics. **Inbound and outbound calls share a single `buildBlandCallConfig` helper in `server/lib/bland.ts`** so neither side can drift on voice, model, prompt builder, dynamic_data URL/headers/body/response_data, analysis_schema, or end-call behavior. The dynamic_data POST body now carries `phone_number` / `call_id` / `from` / `to` (interpolated by Bland), enabling email-on-file and `previous_proposal_info` lookups for inbound callers too. The post-call webhook detects inbound payloads via `metadata.source === "inbound_phone"` (set by `/api/bland/inbound`) and runs a stateless `generateGuestProposalForInboundCall` helper — parses the analysis, resolves caller phone via the priority chain `from` → `phone_number` → `variables.phone_number` → `variables.from`, looks up email via the phone↔email map (falling back to the analysis email and opportunistically promoting it onto the map), then runs the same Duffel search → `buildGuestProposalDataFromOffers` → `createGuestProposal` → `sendGuestProposalEmail` pipeline as the outbound flow, skipping anything that requires a `userId` (no in-app proposal save, no Claude verification). The inbound branch is fire-and-forget so the webhook always ACKs 200 and Bland never retries.
-   **Itinerary Proposals:** After a call, the system automatically generates itinerary proposals by searching **Duffel API** for flights. Proposals include detailed line items, Duffel flight cards, and options for user approval and booking. A "Guest Proposal Flow" allows users to receive and book proposals via email without requiring an account. The guest proposal email is fired in parallel the moment Duffel returns flight results (not after the in-app proposal save + Claude verification finishes), so the caller's email arrives within seconds of the call ending. The three emailed options (Best Price / Best Value / Fastest) are deduped by a flight signature (`carrier+flightNumber|departing_at`) so multiple fares of the same physical flight never appear as three near-identical cards. Booking links resolve their base URL with a production-aware fallback chain (`APP_URL` → hardcoded `https://travnr.com` in production → `REPLIT_DEV_DOMAIN` in dev → localhost), so deployed emails never accidentally point at the dev preview domain.
-   **Guest Booking Flow (no account required):** Each emailed flight option carries a per-option token; clicking "Book This Flight" opens `/book/:optionToken` where the guest enters passenger details and pays via Stripe (Apple Pay / Google Pay supported). The server creates a placeholder unverified user to satisfy the `payments.user_id` FK, then either auto-books on Duffel (if balance is sufficient) and sends an automatic confirmation email, or routes to the existing manual fallback (admin alert + warm "we're on it within 2h" holding email to the guest). The confirmation email links to a pre-filled signup URL (`/auth?mode=register&email=...&name=...&phone=...&claim=...`); the register endpoint promotes the placeholder user when claimed instead of rejecting as duplicate. Concurrency safety: `/confirm` uses an atomic `claimGuestProposalForBooking` that flips the row to a transient `"booking"` status only from `pending|viewed|sent`, then promotes to `"booked"` on success or rolls back on failure. `/payment-intent` and `/option` reject while status is `"booking"` to prevent double-PI races, and `/confirm` auto-refunds duplicate PIs in the `expired` and `already booked` branches (skipped if the PI already backs an existing payment row, so legitimate same-PI retries are never voided).
-   **Flight Management:** Integrated with **Duffel API** for real-time flight search, booking, and order management. This includes multi-passenger support, cabin class selection, and baggage information.
-   **Payment Processing:** **Stripe** is integrated for secure payment collection. Payment intents are created for flight purchases, supporting various payment methods including Apple Pay and Google Pay. The platform uses a pre-funded Duffel balance for actual flight bookings, with customer payments collected via Stripe.
-   **Admin Features:** An admin mode (for `@travnr.com` emails or whitelisted users) provides an administrative dashboard with stats, user management, payment history, and a manual booking fallback system for cases where Duffel balance is insufficient, ensuring bookings can still be processed.
-   **Notification System:** A robust system for user notifications with read/unread states.
-   **Travel Calendar:** A monthly calendar view for managing trip dates.
-   **Legal Pages:** Public `/privacy` and `/terms` pages (in `client/src/pages/privacy.tsx` and `client/src/pages/terms.tsx`, registered in both the signed-out and signed-in route switches in `client/src/App.tsx`) render template Privacy Policy and Terms of Service content marked as pending legal review (see top-of-file comment). Linked from the landing-page footer. Contact emails: `hello@travnr.com` (primary) and `support@travnr.com` (placeholder).

The project structure is organized into `client/`, `server/`, and `shared/` directories, with `shared/schema.ts` defining common database schemas and types across the application.

## External Dependencies

-   **SendGrid:** Used for sending email notifications, specifically for email verification and guest proposal emails.
-   **Duffel API:** Integrated for all flight-related operations, including searching flights, retrieving offer details, and booking flights.
-   **Bland AI:** Provides voice AI capabilities for automated concierge calls, including call dispatch, dynamic data interaction, and post-call analysis (transcripts, recordings).
-   **Stripe:** Utilized for payment processing, handling credit card transactions, and managing payment intents for flight purchases. Integrates via `@stripe/react-stripe-js` on the frontend and server-side webhooks.
-   **PostgreSQL:** The primary database for storing all application data, managed through Drizzle ORM.
-   **Vite:** Frontend build tool.
-   **Tailwind CSS:** Utility-first CSS framework for styling.
-   **shadcn/ui:** UI component library.
-   **TanStack React Query:** For data fetching and caching on the frontend.
-   **bcrypt:** For hashing user passwords.
-   **express-session & connect-pg-simple:** For server-side session management.
-   **wouter:** Client-side router.
