Here is full context on Travnr and what we are building:
Travnr is an AI travel concierge. Users can request a call through the website where they submit a form including their email and phone number, or they can call a Travnr inbound number directly. The AI has a conversation, collects travel preferences, and generates a proposal with flight options. We are restructuring the flow so no account is required to get value — the experience is: call → AI conversation → email with 3 flight options → click to book → account offered post-booking. The dashboard and existing account flow stays intact for existing users.
Change 1 — Phone number to email association
When a user submits any form on the website that includes both a phone number and an email address — whether or not they create an account — store that phone-to-email mapping in the database. Add a phone_email_map table with fields: phone (normalized to E.164 format, unique), email, createdAt, updatedAt.
When an inbound call comes in, look up the caller's phone number in this table first. If a match is found, use that email for the proposal without asking. If no match is found and the caller has no account, only then ask for their email address at the end of the call as a last resort. Frame it naturally: "What email should I send your flight options to?" — not as part of the standard flow but only when genuinely needed.
Change 2 — Updated Bland AI prompt
Update buildTravelConciergePrompt in server/lib/bland.ts:

Assume economy class unless the user specifies otherwise
Assume 1 passenger unless told otherwise
Assume flexible times unless told otherwise
Ask only for what is genuinely needed: where they want to go, where they're flying from, and their travel dates
Do not aggressively clarify airports — if the user says Chicago assume O'Hare, if they say New York assume JFK, if they say LA assume LAX. Only clarify if the city is genuinely ambiguous with no obvious primary airport
Do not ask about loyalty programs, seat preferences, dietary needs, or other secondary details on the first call
If the email was pre-loaded from the phone lookup, do not ask for it
If no email was found via phone lookup, ask for it naturally at the end: "What email should I send your options to?" — only once, do not repeat
Close with: "Perfect — you'll have your options in your inbox within a minute. Talk soon." then GOODBYE immediately
Update the <TRAVEL_DETAILS> JSON block to include an email field (can be null if not collected and not found via phone lookup)

Change 3 — Guest proposal database and public page
Add a guest_proposals table: id, token (unique random UUID), email, originIata, destinationIata, departureDate, returnDate, passengers, cabinClass, proposalData (JSON with 3 flight options), status (pending/viewed/booked/expired), createdAt, expiresAt (24 hours after creation).
Each of the 3 flight options in proposalData should have its own unique booking token so each option has its own direct booking link.

If expired, automatically trigger a fresh Duffel search for the same route in the background, generate a new guest proposal with a new token, send it to the user's email immediately, and return { expired: true, refreshed: true } so the frontend can show the right message.

Change 4 — The 3 flight options logic
When generating options for the guest proposal, always return exactly 3 options:

Option 1 "Best Price": Cheapest available regardless of stops
Option 2 "Best Value": Nonstop or fewest stops with price no more than 30% above cheapest
Option 3 "Fastest": Shortest total travel time regardless of price

If fewer than 3 distinct options exist fill with next best alternatives. Label each clearly on the proposal page and in the email.
