## 1. Plain-English answer: what failed this time?

The second WSSS run did not fail because Replit died.

The server stayed reachable. The WSSS provider subscription was created. The runtime session was active. The detached supervisor remained alive. The callback watchdog did not trigger. The run stayed alive for about the full intended two-hour exposure.

The failure happened at the end, when our code performed a credit-accounting cross-check.

The program compared:

1. External provider spend: how many Flight Alert credits disappeared from the AeroDataBox account balance during this run.
2. Internal received-delivery spend: how many credits/items our own webhook-delivery records said we received and accounted for.

The strict rule was:

PASS only when EXTERNAL equals INTERNAL.

For P2G06 they were not equal, so the code correctly refused to mark WSSS as a valid completed scientific result.

Final durable state:

- status = failed
- reconciliation_status = MISMATCH
- stop_reason = external_internal_credit_mismatch
- duration_censored = false

This is a different failure class from the original WSSS attempt.

## 4. What is a webhook?

A webhook is simply a URL on our server that AeroDataBox calls when it has an update.

Simplified flow:

AeroDataBox Flight Alert subscription
  -> sends HTTP POST
  -> Replit callback URL
  -> temporarily store raw body
  -> record delivery accounting
  -> record temporary flight/item information
  -> answer HTTP 2xx when successful

The important provider billing fact is that Flight Alert credits are charged when the notification is sent, not only when our server successfully receives and stores it.

AeroDataBox's January 31, 2026 Flight Alert guide says:

- credits are deducted when a notification is sent to the webhook;
- the cost is one credit per flight item;
- if the endpoint is down or delivery fails, the send can still be charged;
- retries, when enabled, also cost credits.

Our Stage-1 code creates subscriptions with maxDeliveryRetries = 0, so provider retry multiplication was intentionally disabled.

Official provider reference:
https://aerodatabox.com/flight-alert-api-2026/

## 5. What is the likely mismatch mechanism?

The strongest structural possibility is:

AeroDataBox sends notification
  -> provider deducts credit(s)
  -> that specific callback delivery does not become a durable internal record
  -> external provider debit becomes larger than local received-delivery accounting

Possible reasons include a network timeout, non-2xx callback response, handler failure, raw-persistence failure, or other failure before durable internal accounting.

That would produce EXTERNAL greater than INTERNAL and the exact reconciliation rule would fail.

But we cannot claim this exact mechanism is proven for P2G06 because the failure path did not retain the numerical internal total or per-request outcome counters.

Other possibilities still open:

1. a callback POST reached Replit but failed before durable accounting;
2. our interpretation of deliveryAttempt.costCredits versus fallback notification_items did not match provider billing semantics for one or more deliveries;
3. an unrelated account-level debit occurred during the interval.

The third possibility is less supported because fresh preflight, unattended health, and the post-run check found no foreign active billable subscription.

## 7. What does transient mean?

Transient means temporary working data.

During a live probe we temporarily need information such as:

- which runtime session owns this probe;
- the provider subscription binding;
- each webhook delivery;
- item-level identifiers needed to calculate distinct flights and chains.

Those details are needed to compute the final research aggregates, but the project deliberately does not want all provider-identifying runtime details stored permanently.

Architecture:

temporary detailed working data
  -> calculate safe aggregate scientific evidence
  -> keep safe aggregate evidence long-term

Transient is the temporary working-data layer.

## 8. What does PostgreSQL UNLOGGED mean?

PostgreSQL normally writes table changes into its WAL/recovery log so the database can recover them after a crash.

An UNLOGGED PostgreSQL table does not put its row contents into the normal crash-recovery log.

The project uses three UNLOGGED runtime tables:

- clean.prepaid_probe_session_runtime
- clean.prepaid_probe_delivery_runtime
- clean.prepaid_probe_item_runtime

Plain English:

LOGGED table = durable evidence intended to survive recovery.

UNLOGGED runtime table = temporary scratchpad used while the probe is running.

The UNLOGGED design itself is not the mistake.

The mistake is that when a mismatch happened, we did not first copy the safe aggregate diagnostic numbers into a durable evidence record before the temporary scratchpad was cleaned.

## 9. Why did the post-run queries show zero runtime rows?

After the child returned a failed result, the supervisor invoked fail-closed recovery.

Recovery exited successfully.

The recovery/cleanup path removes the exact owned temporary session, delivery rows, item rows and purpose-bound raw blobs when appropriate.

That is why the later SQL query showed zero session, delivery, and item runtime rows.

Those zeros do not prove the run had zero deliveries.

They prove the temporary rows had been cleaned by the time the user queried them.

Because no durable mismatch receipt preserved the aggregate internal count before cleanup, that exact number was lost.

## 12. Engineering defects exposed by P2G06

### Defect A — mismatch numbers not durably preserved

The live-window function had externalCredits, internalSendCredits, maxObservedUnsettledCreditGap, settlementReads, and metrics.

The durable failure update preserved only failed status, stop reason, runtime session ID, reconciliation status, and optional cleanup timestamp.

That is why we know MISMATCH but not the exact internal count now.

### Defect B — callback outcome accounting is insufficient for diagnosis

We need safe durable aggregate counters for:

- callback requests seen
- callback successful 2xx
- callback 4xx
- callback 5xx
- raw persistence failures
- runtime database failures

### Defect C — mismatch cleanup order needs a durable evidence checkpoint

Required order must become:

stop/delete provider subscription
  -> settle provider balance
  -> calculate external/internal/delta
  -> WRITE SAFE DURABLE RECONCILIATION RECEIPT
  -> cleanup transient runtime/raw-purpose data
  -> write final probe PASS/FAIL

### Defect D — terminal mismatch left budget day OPEN

After P2G06, P2G-S1-20260921-05 remained OPEN while probe 4 was already terminal failed/MISMATCH.

A terminal reconciliation failure must deterministically terminalize the budget day into the existing appropriate mismatch/failure state.

It must not be silently marked as a successful close.

### Defect E — generic failure return hardcodes censoring

The inner live-window result correctly knew P2G06 reached full duration: duration_censored=false.

But the outer generic failed-result return currently returns durationCensored=true.

The durable row stayed correct, but caller/log evidence can become contradictory.

The failure result must propagate the actual inner censoring value.

### Fix 4 — in-run reconciliation-gap evidence

At each balance/internal-accounting poll, record safe interval evidence:

- poll timestamp
- external delta so far
- internal total so far
- current gap
- consecutive gap count

### Fix 5 — pre-frozen persistent-gap stop rule

A temporary gap can exist because provider accounting and callback processing are not perfectly simultaneous.

Therefore do not fail on one instantaneous difference.

But do not knowingly spend two hours if the gap remains persistently unreconciled.

Before the next paid WSSS run, freeze and test a rule that terminates exposure fail-closed if an external-versus-internal gap remains nonzero beyond the configured grace/settlement sequence.

The exact grace must be chosen before the paid run, not after seeing Tuesday's result.

### Fix 6 — mismatch budget terminalization

external_internal_credit_mismatch must terminalize the budget day into the correct mismatch/failure state.

### Fix 7 — fix censoring propagation

Return the real inner durationCensored value, not unconditional true, for the generic failed-result path.

### Fix 8 — add offline regression tests for this failure family

Required cases:

1. provider debit + successful callback -> MATCH;
2. provider debit + callback never arrives -> mismatch;
3. callback reaches server but returns non-2xx;
4. raw persistence fails before 2xx;
5. internal costCredits differs from item-count fallback;
6. exact match after settlement;
7. persistent mismatch after settlement;
8. mismatch receipt survives transient cleanup;
9. mismatch terminalizes budget day;
10. failed full-duration result remains duration_censored=false;
11. mismatch can never become PASS;
12. no second paid launch is triggered automatically.

## 18. Why 6 is more defensible than 3 or 5

The frozen frame uses six macro-regions:

1. North America
2. Europe
3. Asia-Pacific
4. Gulf/Africa
5. South America
6. Oceania

A compact six-airport design can keep one already-frozen candidate from every region.

That gives better structural representation than choosing only three.

Five airports cannot cover all six macro-regions simultaneously.

General NIST sampling guidance says adequacy depends on representativeness, sample size, population variability, desired precision, and cost/practicality.

NIST also notes that stratification and prior information can reduce required sample sizes, while smaller samples accept lower precision.

References:
https://www.itl.nist.gov/div898/handbook/ppc/section1/ppc134.htm
https://www.itl.nist.gov/div898/handbook/ppc/section3/ppc333.htm

Aviation delay literature also treats airport behavior as heterogeneous by airport/network characteristics, supporting deliberate diversity rather than assuming every hub is interchangeable.

Example:
Diana, T. (2009), Do market-concentrated airports propagate more delays than less concentrated ones? A case study of selected U.S. airports, Journal of Air Transport Management.
https://www.sciencedirect.com/science/article/abs/pii/S0969699708001774

No source in the current Plan establishes 12 as a universal scientific minimum. Twelve was a project-specific design choice.
