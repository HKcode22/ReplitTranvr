## 2. Domestic versus international: what it means technically

Domestic/international is a route property and an airport-network feature.

For one route:

    origin country == destination country  -> domestic
    origin country != destination country  -> international

For each airport, Plan §4.5 defines an international-share quantity:

    intl_share
      = international departures
        / departures with a known country pair

That value participates in two exogenous airport features:

    geo_score
      = 0.5 * degree_norm
      + 0.3 * intl_share
      + 0.2 * region_rarity

    carrier_score
      = 0.6 * effective_carriers_norm
      + 0.4 * intl_share

Therefore "domestic versus international" is not a rule that an airport must be in the U.S.

An airport such as WSSS can be a global HUB candidate and have an international-share value describing the mix of its routes.

## 3. What an anchor airport is

The later experiment cannot treat every airport identically because provider cost, available observation time and coverage are finite.

The design therefore selects a final pool of five anchor HUB airports.

An anchor is intended to be a repeatedly useful HUB point in the later sampling design.

A candidate needs four kinds of evidence:

1. traffic/capacity;
2. geographic/network structure;
3. carrier/international diversity;
4. observed provider yield.

The frozen anchor score is:

    anchor_score
      = 0.40 * traffic_score
      + 0.20 * geo_score
      + 0.20 * carrier_score
      + 0.20 * yield_score

Capacity is a separate feasibility gate:

    rows_per_hour >= 60

The first three score components come from exogenous reference data frozen before Stage 1.

The fourth component, yield_score, comes from live Stage-1 measurements.

This means a two-hour probe does not determine the entire airport score by itself.

## 4. What Stage 1 is actually measuring

Stage 1 is not the final ML data collection.

It is a standardized airport-measurement experiment.

For each valid candidate, the experiment targets a two-hour matched weekday/time-class exposure and records:

    rows delivered
    rows per hour
    confirmed distinct flights
    confirmed unique flights per Alert credit
    tail-chain links
    tail-chain links per Alert credit
    delivery stability
    complete 15-minute bucket count
    identity ambiguity lower/upper bounds
    actual duration
    censoring/stop reason
    runtime cleanup proof
    reconciliation status

The goal is to compare candidate airports under the same measurement protocol.

Later Stage 2 takes the top five capacity-passing candidates and performs longer four-hour confirmation probes.

Only after that is the final five-airport anchor pool established.

## 5. Yield-reference normalization: the old "calibration" term

The binding Plan renamed the old Stage-1 word "calibration" to "yield-reference normalization."

That avoids confusion with later ML probability calibration.

Current Stage-1 yield has three components:

    unique_flights_per_credit
    tail_chain_links_per_credit
    stability

### 5.1 Unique flights per credit

Conceptually:

    confirmed distinct physical flights observed
    --------------------------------------------
    reconciled Alert credits

Repeated updates for one flight do not count as different physical flights.

### 5.2 Tail-chain links per credit

If the same aircraft registration appears across compatible distinct flight legs, the experiment can link those legs into an aircraft rotation chain.

Conceptually:

    useful confirmed tail-chain links
    ---------------------------------
    reconciled Alert credits

This matters because aircraft operational state can propagate from one leg to another.

### 5.3 Stability

The target window is split into complete 15-minute buckets.

The coefficient of variation is:

    CV = standard_deviation(bucket_counts) / mean(bucket_counts)

The frozen stability transform is:

    stability = 1 / (1 + CV)

Therefore:

    lower variability -> stability closer to 1
    higher variability -> stability closer to 0

### 5.4 WSSS and OMAA as references

The frozen Plan specifies:

    WSSS = primary yield reference
    OMAA = permitted fallback reference

WSSS is not a "U.S. baseline."

It is simply the pre-frozen reference airport used for Stage-1 yield normalization.

For each component:

    component_std
      = clamp(candidate_component / reference_component, 0, 1)

Example:

    reference unique flights/credit = 0.30
    candidate unique flights/credit = 0.24

    candidate/reference = 0.24 / 0.30 = 0.80

The component standardized value is 0.80.

If a candidate exceeds the reference, clipping caps that component at 1.0.

The final yield component is:

    yield_score
      = (unique_std + chain_std + stability_std) / 3

Yield is only 20% of the total anchor score.

Current complication: WSSS did not produce a valid normal two-hour measurement because its run was infrastructure-interrupted. OMAA did produce a valid completed result and the Plan contains an OMAA fallback rule for an invalid WSSS reference. Whether WSSS/MMUN receive a controlled infrastructure-invalid rerun still must be reconciled before the next paid weekday run.

The current prepaid webhook path is:

    AeroDataBox
        |
        | HTTPS POST
        v
    Replit public .replit.dev address
        |
        v
    server/index.ts
        |

        v

        | POST /api/v1/webhooks/aerodatabox/:secret/prepaid/:sessionId
        v
    persistPrepaidProbeWebhookV39(...)
        |
        +-----------------------------+
        |                             |
        v                             v
    Replit Object Storage         PostgreSQL runtime
    raw provider bytes            UNLOGGED session/delivery/item rows

The prepaid route checks the webhook secret and session ID.

It calls persistPrepaidProbeWebhookV39.

Only after the persistence operation succeeds does routes_v3.ts return HTTP 200 with a received/items/duplicate response.

If persistence throws an error, the route records an incident and returns a server error rather than claiming the notification was safely saved.

## 8. Where the data is saved

There are deliberately separate storage layers.

### 8.1 Raw provider bytes: Replit Object Storage

The exact raw webhook body is written to Replit Object Storage.

PostgreSQL stores metadata about that object in:

    clean.provider_content_blob_ref

That metadata includes items such as:

    object identity/reference
    content SHA-256
    byte count
    persisted timestamp
    expiration timestamp
    deletion verification timestamp/run

The workspace health contract currently reports a bounded raw retention value of 168 hours.

Purpose-completion cleanup may delete the raw object earlier after the probe has safely produced the required aggregate evidence.

The object-reference/tombstone record can remain as proof that an object existed, had a particular hash, and was later deletion-verified without retaining the provider bytes.

### 8.2 Temporary probe working state: PostgreSQL UNLOGGED tables

The temporary runtime tables are:

    clean.prepaid_probe_session_runtime
    clean.prepaid_probe_delivery_runtime
    clean.prepaid_probe_item_runtime

Session runtime stores information such as:

    which probe owns the session
    stage
    state: armed / active / settling
    provider subscription binding
    last-delivery information

Delivery runtime stores information such as:

    delivery identity
    raw body hash/blob reference
    receive time
    provider notification/attempt evidence
    notification item count
    delivery cost evidence

Item runtime stores information such as:

    flight number
    aircraft registration
    codeshare status
    runtime flight key
    receive time

These tables are working memory for the current live probe.

They are not intended to be the final long-lived research dataset.

### 8.3 Durable Stage-1 result: clean.adb_anchor_probe

Before provider creation, the execution path reserves a durable row in:

    clean.adb_anchor_probe

with:

    status = probing

It also durably binds the random runtime-session UUID to that probe row.

This is important because PostgreSQL UNLOGGED tables can disappear/reset under certain database/runtime failures. The durable UUID still tells recovery which live session belonged to which probe.

If the probe completes safely, clean.adb_anchor_probe is updated with:

    status = completed
    actual window start/end/hours
    rows delivered
    confirmed unique flights
    tail-chain links
    rows/hour
    unique flights/credit
    chain links/credit
    stability
    complete bucket count
    identity lower/upper bounds
    runtime session ID
    runtime cleanup verification timestamp
    reconciliation_status = MATCH

If the probe fails, the durable row remains and is updated to failed with the stop reason and available safe reconciliation/cleanup evidence.

That is why WSSS/MMUN are still permanently visible as failed attempts even after transient cleanup.

### 8.4 Audit/evidence files

Separate artifacts contain:

    runtime definition
    authorization record
    callback verification receipt
    supervisor status
    supervisor heartbeat
    persistent log
    evidence-ledger records

These provide reproducibility across code, authorization, runtime and scientific result.

## 9. Why successful cleanup intentionally produces 0/0/0

After metrics and reconciliation are safe, purpose-completion cleanup deletes:

    clean.prepaid_probe_item_runtime
    clean.prepaid_probe_delivery_runtime
    clean.prepaid_probe_session_runtime

and verifies that no live raw provider blob remains for that runtime session.

Therefore this is healthy:

    sessions = 0
    deliveries = 0
    items = 0
    live_blobs = 0

It does not mean the scientific result disappeared.

The durable clean.adb_anchor_probe row remains.

Technical analogy:

    runtime tables = scratch workspace
    adb_anchor_probe = final measured result

## 10. What "runtime" means

Runtime means the state of software while it is actually executing.

This project has several runtime levels.

### 10.1 Operating-system process runtime

Examples:

    npm run dev
    tsx --watch server/index.ts

These are real operating-system processes with PIDs inside Replit.

If they terminate, the callback server disappears.

### 10.2 Application runtime

Inside that process, the Express application contains:

    registered routes
    environment/config values
    startup Git SHA
    HTTP listener on port 5000
    runtime-health endpoint

### 10.3 Probe runtime

During a paid probe, additional runtime state exists:

    runtime session UUID
    active provider subscription binding
    temporary session/delivery/item rows
    supervisor process
    heartbeat
    callback watchdog
    current budget-day state

Runtime is not equivalent to source files stored on disk.

It is possible to have:

    files checked out at Git SHA B
    already-running Node process started from Git SHA A

until the process is restarted.

That exact condition occurred during weekend hardening and was correctly rejected.

## 11. What "long-lived real database" means

This is not a different kind of PostgreSQL product.

A fresh test database starts empty:

    empty database
        ->
    run migrations
        ->
    current schema

A long-lived database is the same persistent database that has already experienced:

    older schema
        ->
    migrations
        ->
    data inserted
        ->
    later migrations
        ->
    newer data
        ->
    application restarts

It contains historical state.

The migration-0022 problem was an upgrade/replay problem.

The current database already contained modern V3.9 frame rows and the modern 0057-era tier-source contract.

During application startup, the migration chain replayed earlier migration 0022.

Old 0022 tried to recreate an obsolete constraint before later migrations 0028/0057 could remove/replace it again.

Modern rows such as traffic_reference / missing_reference did not satisfy that obsolete rule.

So boot failed at 0022.

The fix made 0022 recognize that the modern v2 constraint already exists and refuse to resurrect the obsolete constraint.

After the repair:

    targeted migration tests passed
    explicit migration replay reached 0057
    DB verifier returned 123/123 PASS
    a genuine Replit managed restart reached 0057 without a new boot failure

A newly created development database can hide some history-dependent upgrade bugs because it has not accumulated the same earlier states/data.

That is why testing both fresh-schema behavior and real upgrade/replay behavior matters.

## 12. Server, index.ts and routes_v3.ts

These are different responsibilities.

### 12.1 "Server"

The server is the running Node/Express application.

It is not synonymous with a single file.

### 12.2 server/index.ts

server/index.ts is the application entrypoint.

It:

    creates the Express app
    creates the HTTP server
    applies boot migrations
    imports ./routes_v3
    calls registerV3Routes(app)
    registers the V3.9 workspace-runtime health route
    registers the rest of the application
    listens on port 5000

Therefore index.ts owns the server lifecycle.

### 12.3 server/routes_v3.ts

routes_v3.ts does not independently listen on port 5000.

It receives the Express app from index.ts through:

    registerV3Routes(app)

and attaches AeroDataBox endpoints.

The current prepaid callback route is:

    POST /api/v1/webhooks/aerodatabox/:secret/prepaid/:sessionId

Therefore routes_v3.ts owns the specific AeroDataBox route behavior.

### 12.4 Why V3 routes are registered before generic routes

index.ts deliberately registers V3 AeroDataBox routes before the generic registerRoutes call.

The source comments explain why: generic CSRF/limiter middleware could otherwise reject an AeroDataBox webhook POST because AeroDataBox is not a browser and does not have the application's browser CSRF token.

So route ordering is part of callback correctness.

## 13. The route_owner mismatch that stopped P2G05

The health endpoint reports:

    route_owner = server/index.ts+server/routes_v3.ts

That is describing two ownership layers:

    server/index.ts
        owns process / HTTP server / port / lifecycle

    server/routes_v3.ts
        owns the prepaid AeroDataBox callback route

Earlier verification code still expected only:

    server/routes_v3.ts

After architecture hardening, that expectation was stale.

The live callback itself was healthy.

The verifier rejected it because the verifier's expected ownership string no longer matched the correct architecture.

That is why P2G05 stopped before paid launch.

This is a software-contract mismatch, not an AeroDataBox failure and not an LKPR scientific failure.

## 14. Why the health endpoint reports the startup Git SHA

At application startup, workspaceRuntimeHealth_v39 reads:

    git rev-parse HEAD

and stores that value as startupGitHead.

GET /__v39/workspace-runtime returns that frozen startup value.

This is intentional.

Example:

    08:00 app starts from commit A
    09:00 git pull changes workspace files to commit B
    09:05 old process from A is still serving port 5000

Then:

    shell Git HEAD = B
    running health startup SHA = A

That mismatch proves the live process has not restarted onto the files currently on disk.

This exact condition occurred during weekend hardening.

The fail-closed callback-prep script rejected the mismatch rather than allowing a paid run on uncertain code.
