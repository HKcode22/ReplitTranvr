### Plain-technical explanation — what all of this means

> The user asked for a **plain-technical-English** walkthrough of the jargon in these reports. This is that glossary, so the tables above are readable.

#### The evidence header fields (why every report has this block)

| Field | Plain meaning |
|-------|---------------|
| `evidence_id: RUN-…` | A unique, immutable ID for this run so we can cite it later (audit trail). `RUN-YYYYMMDD-NNN` = run reports; `GATE-…`/`AUTH-…`/`ISS-…`/`DEC-…` are other record families defined in the plan/log. |
| `gate_id: null` | Which gate this run belongs to. `null` means "Phase-0 offline work, no gate yet" (gates only appear once Phase 0 closes). |
| `authorization_id` | The exact human authorization record that permits a paid/live action. `user-authorized (no spending)` = you told me to proceed, but only offline/non-spending commands ran. |
| `result: PASS / PARTIAL / BLOCKED` | The run's outcome using the canonical status vocabulary (§0.6). `PASS` here means "this work package passed," **not** "Phase 0 is done." |
| `git_inspected_commit` | The exact GitHub commit (`SHA`) that the current repository state is being judged against (`5bffdaf…`). The log pins this so "current" means a specific code state, not "whatever changed last." |
| `command_interface` | Exactly what was run (`vitest run`, `tsc --noEmit`, `npm run build`, …). Readable + reproducible. |
| `exit_code: 0` | The OS exit status. `0` = the command finished without error. (Per §4.4, exit 0 is **not** the same as scientific PASS.) |
| `auto_collect: ADB_AUTO_COLLECT=0` | The safety variable proving collection is OFF. Because of CRIT-001 we now use the literal `0` (not `"false"`). |

#### What "Phase 0" and "Gate 0" mean

- **Phase 0** is the **offline implementation/verification phase**: no provider calls, no credits spent. Its exit contract (§1.5) is long: fail-closed runtime, raw-before-2xx, FIDS/DST, identity-v2, snapshots, outcomes, accounting, calendar, manifest, migrations, the full TEST-001–028 matrix, typecheck/lint/build = 0, and an **aggregate** preflight. It is currently **BLOCKED** because many of those are not yet done.
- **Gate 0** is the **first live/account phase** (Phase 1). It reads the actual AeroDataBox account/budget. It is **after** Phase 0 — you cannot run Gate 0 while Phase 0 is blocked. (The read-only balance/subscription evidence we gathered is "provenance," not a Gate-0 PASS.)

#### What CRIT-001…014 are

`CRIT-` = "critical repository finding" from the latest inspection (§0.2). They are **current-code defects** that must be repaired in Phase 0 before any paid work. The ones touched so far:
- **CRIT-001** — `ADB_AUTO_COLLECT !== "0"` was fail-open (any value ≠ `"0"` meant collection ON). Fixed to explicit opt-in; now tested.

## 10. What AUTH Is and Why We Need It

### AUTH ≠ API key

| Thing | What it is | What it lets us do |
|-------|-----------|--------------------|
| **API key** | A credential to talk to AeroDataBox | Call the API (read balance, query flights) |
| **AUTH record** | A formal, time-boxed, scoped approval | Spend credits / create subscriptions / refill |

### Why the system demands it

1. **Protects your credits** — an AUTH caps spend and duration.
2. **Audit trail** — every paid action is traceable to an approval.
3. **Scope limiting** — names the exact airport/filter/window, ceiling, stop owner.
4. **Automatic stop** — refuses when AUTH expires or a ceiling is hit.

### What you gave me vs what I still need

- ✅ **API key** — good for the **non-spending** Gate 0 read.
- 🔒 **For spending actions**, I will bring you a concrete AUTH record to approve. I will not spend without it.
