# 1. Vocabulary hierarchy — Phase vs Gate vs Stage vs Probe

A lot of confusion came from using these words as if they meant the same thing. They do not.

| Level | Technical meaning | Current example |
|---|---|---|
| **Phase** | Large project block with a distinct purpose and risk level. | Phase 0 = engineering foundation; Phase 2 = live-readiness + Gate-2 probing. |
| **Gate** | Admission checkpoint. A later operation is forbidden until its predecessor evidence passes. | Gate 1 checks provider coverage; Gate 2 is the anchor-probe selection protocol. |
| **Stage** | Sub-experiment inside a gate. | Gate 2 has Stage 1 and Stage 2. |
| **Probe** | One bounded paid live experiment for one airport. | OMAA's 120-minute Stage-1 probe. |
| **Runtime artifact** | Frozen machine-readable rules for one attempt. | `phase2g-gate2-runtime-P2G-S1-20260917-03.json`. |
| **AUTH** | Human-approved permission envelope tied to exact bytes/hashes/scope/time/credit cap. | `AUTH-20260917-P2G04`. |
| **Preflight** | Fresh read-only admission check immediately before launch. | Must say `PASS_READY_FOR_PAID_STAGE1`. |
| **Budget day** | Immutable accounting envelope associated with the attempt. | `P2G-S1-20260917-03`. |
| **Handoff** | Evidence that the prior gate/stage passed sufficiently to prepare the next one. | Phase-2F smoke handoff allowed Phase-2G preparation. |
| **Terminal** | Attempt state that the Stage-1 owner does not simply repeat in-place. | `completed`, `failed`, `abandoned`. |

Think of the hierarchy as:

```text
Phase 2
└── Gate 2
    ├── Stage 1

    │   ├── OMAA probe
    │   ├── MMUN probe
    │   └── ...
    └── Stage 2
```

# 2. The four kinds of state in this experiment

The system deliberately separates four different kinds of state because mixing them was a major corruption risk.

## 2.1 Scientific design state

Examples: sampling frame, shortlist order, replacements, time class, normalization caps. This is frozen *before* seeing outcomes so we cannot adapt membership after looking at which airports perform well.

## 2.2 Authorization/accounting state

Examples: AUTH file, budget-day ID, 450-credit reservation, 50-credit guard band, 500-credit hard envelope. This exists to prevent accidental or unbounded provider spend.

## 2.3 Live transient runtime state

Examples: current prepaid session, current delivery/item bookkeeping, provider subscription binding. These are intentionally kept in PostgreSQL `UNLOGGED` runtime tables because they are operational working state rather than long-lived research evidence.

## 2.4 Durable audit/scientific evidence

Examples: final `adb_anchor_probe` result, runtime-session UUID binding, status, aggregate metrics, reconciliation, cleanup timestamp, artifact hashes, bounded raw-provider blob references, run logs, AUTH/preflight/runtime hashes.

That separation explains why after OMAA completed the transient runtime tables could be empty while the experiment was still fully saved in the durable result/evidence layer.

# 3. Phase 0 — what we actually built and why

Phase 0 was the offline engineering/safety foundation. The purpose was **not** to collect the final research dataset. It was to make the later live system fail closed instead of silently continuing when assumptions break.

Formal Phase-0 closure occurred on **2026-09-09** on tested code SHA `022bc3933b6e6928293e7c6a8ce86d45aa2b3493`, with GitHub Actions run `34345546738` successful. Fresh schema, migrations, migration replay, schema verification, TypeScript, unit/integration tests, lint, registry, traceability, contradiction scanner, aggregate preflight, and production build passed while provider collection was OFF.

## 3.1 0A — runtime fail-closed behavior

Core idea: a missing or malformed environment variable must mean **OFF**, not “probably on.” `ADB_AUTO_COLLECT` was changed to explicit opt-in semantics. Experimental delivery retries are forced to zero. Why: a typo must never start an expensive collection path.

## 3.2 0B — raw-before-2xx webhook persistence

The webhook path is designed so the normalized immutable raw envelope/items are durably accepted before the provider receives a successful HTTP acknowledgement. Why: returning `2xx` before durable persistence could make the provider think a delivery succeeded even if our system lost it.

## 3.3 0C — FIDS/population contract

This work established local-date/DST-safe FIDS handling, requested-vs-context population roles, bounded retries, and provider contract tests. Why: a flight close to midnight can belong to a different service date locally than in UTC; getting this wrong changes population membership.

## 3.4 0D — canonical flight identity

Provider IDs are not the scientific identity key. The project builds a canonical flight identity from stable flight facts and treats retimes as schedule versions of the same physical flight rather than inventing a new flight every time a schedule moves. Why: provider identifiers and scheduled times can change.

## 3.5 0E — semantic events and deduplication

Semantic observations have their own stable identity rules. Why: two meaningful events can occur at similar times and must not collapse just because one timestamp happens to match.

## 3.6 0F / 0G / 0H — PRE, AIRBORNE, and outcome builders

PRE snapshots only use information whose `available_at` is at or before the prediction cutoff. AIRBORNE logic preserves observation cadence/trajectory behavior. Outcome terminalization keeps each target's observed/censored/missing state separate. Why: this is the anti-leakage layer.

## 3.7 0I — history/weather as-known logic

Historical and weather features have to be represented as they would have been known at the cutoff, not as corrected/revised values learned later. Why: training on future-corrected information would inflate model performance.

## 3.8 0J — frame/anchor machinery

This includes airport frame eligibility, tier/reference inputs, anchor-scoring inputs, and later capacity/yield logic. Why: candidate membership must come from a reproducible rule, not human preference after outcomes appear.

## 3.9 0K — settlement and credit accounting

External provider balance movement is compared with the project's internal send accounting. Budget-day exposure is guarded. Why: “the script exited 0” is not enough; we need to know whether the provider charged what the system thinks it charged.

## 3.10 0L — experiment calendar/crossover rules

Calendar/time-class and crossover/washout constraints were encoded so later timing is not opportunistically changed after looking at results.

## 3.11 0M — manifest and split rules

Hashes/version identities connect a dataset/result to the exact code/reference/config that produced it. Why: a later model result must be reproducible against a specific experiment state.

## 3.12 0N–0Q — migrations, command owners, tests, typecheck/lint/build/preflight

The repository had to prove its command surface was real rather than placeholder stubs, migrations were replay-safe, tests covered required behaviors, and the project built cleanly.

Phase 0 did **not** promise that a Replit development container could never restart. The later WSSS run exposed exactly such a live-runtime boundary; the correct response was to preserve the failure and repair that boundary.

# 12. Stage 1 — end-to-end mechanics of one probe

This is the most important section for understanding what actually happens technically.

## Step 1 — identify the next frozen candidate

The owner reads the exact preprobe artifact + durable Stage-1 evidence. Terminal statuses are `completed`, `failed`, `abandoned`. It selects the first primary whose status is not terminal.

For the next attempt that is MMUN.

## Step 2 — freeze a new runtime/budget day

A runtime JSON is created for one attempt. It binds the preprobe/smoke predecessors, immutable budget-day ID, minimum stability buckets, reservations, guard band, settlement controls, and evidence IDs.

## Step 3 — create a DRAFT AUTH

The AUTH builder creates a file but labels it `DRAFT_ONLY_NOT_AUTHORIZED`. Merely having the JSON file does not allow spending.

## Step 4 — human review/approval

The human approves the exact AUTH ID + exact SHA + exact scope + maximum credits. The approval helper re-hashes the file, validates predecessor IDs, runtime binding, Stage-1-only scope, credit ceiling, cleanup owner, and time window, then records the approval in the evidence ledger.

## Step 5 — prepare/verify workspace callback

Gate-2 currently uses the Replit development `.replit.dev` callback, not `travnr.com`, because the project rule forbids redeployment before Phase 6. The callback helper ensures the current workspace server exposes the V3.9 health endpoint and uses provider-blob safe mode.

## Step 6 — fresh paid preflight

Immediately before launch, `v39_phase2g_stage1_paid_preflight_v39.ts` rechecks the world *as it exists now*. It checks:

- local Git HEAD equals the authorized execution SHA;
- AUTH bytes hash exactly to the approved SHA;
- AUTH scope equals the runtime/preprobe binding;
- evidence ledger contains the exact approval;
- AUTH timing is valid;
- no unresolved incidents;
- no active Stage-1 probe;
- this budget day has no previous probe rows;
- no other budget day is OPEN;
- provider balance leaves protected headroom;
- no active foreign/billable provider subscription exists;
- `.replit.dev` callback is reachable and source-compatible;
- provider blob-bucket configuration is valid;
- current weekday/time is inside the frozen Stage-1 class;
- enough AUTH duration remains for 120 minutes + cleanup;
- the run will not cross UTC midnight.

Only exact `PASS_READY_FOR_PAID_STAGE1` with zero blockers is launchable.

## Step 7 — hash the preflight receipt

The launcher is not told “preflight passed, trust me.” It receives the actual receipt file + SHA. If any byte changes or the receipt is older than the launch freshness limit, it refuses.

## Step 8 — launch through the guarded front door

`v39_phase2g_stage1_launch_logged_v39.sh` rechecks AUTH/runtime/preprobe/preflight hashes, exact HEAD, callback reachability, and environment. It never calls the provider if these guards fail.

## Step 9 — spawn detached supervisor

A Node spawner creates the Stage-1 supervisor in a separate OS session/process group. This is why ordinary browser/terminal disconnects are less likely to kill the live owner than in the first WSSS implementation.

## Step 10 — Stage-1 owner reselects the target from frozen evidence

Even though we know MMUN is next, the owner itself re-derives the next frozen candidate. An explicit ICAO cannot be used to skip the owner-selected airport.

## Step 11 — incident, overlap, coverage, balance, and R1 checks

Before subscription creation, the prepaid execution path verifies no unresolved incident, no overlapping probing row, known coverage, sufficient provider balance, and no foreign active billable subscription.

## Step 12 — reserve durable conservative exposure

A durable `clean.adb_anchor_probe` row is created with `status='probing'`. In provider-content-safe mode the durable reserved exposure equals:

```text
stage1 reservation 450
+ unsettled-burst margin 50
= conservative protected exposure 500 Alert credits
```

## Step 13 — arm a random runtime session

The live-window code creates a random runtime-session UUID in transient runtime state.

## Step 14 — durably bind that random UUID BEFORE provider creation

This is the key WSSS repair. The UUID is written into the logged `adb_anchor_probe.runtime_session_id` before the provider subscription may be created. If UNLOGGED runtime disappears later, recovery still knows the exact deterministic callback identity.

## Step 15 — create exactly one owned provider subscription

The paid live window creates the exact `CreditBased`, `FlightByAirportIcao`, WebHook subscription for the current airport/callback.

## Step 16 — receive callbacks

Provider deliveries arrive at `/prepaid/<runtime-session-uuid>`. Raw provider bytes go to the bounded App Storage object boundary. Transient item/session bookkeeping stays in UNLOGGED runtime. Durable long-lived provider plaintext is intentionally avoided in ordinary logged PostgreSQL.

## Step 17 — collect for the target window

Stage 1 targets 120 minutes. The supervisor emits heartbeat evidence and checks the callback every 15 seconds. Three consecutive callback failures trigger fail-closed termination/recovery behavior.

## Step 18 — delete the exact owned subscription

At the end or on controlled failure, the code operates only on positively owned subscription identity. No bulk deletion.

## Step 19 — settlement/reconciliation

The system stabilizes provider balance reads and compares external observed spend with internal send accounting according to the frozen settlement rules. Successful Stage-1 completion requires reconciliation `MATCH`.

## Step 20 — cleanup transient runtime

Provider-sensitive session/delivery/item runtime state is cleaned after the provider subscription is gone and storage/runtime cleanup is verified.

## Step 21 — compute scientific aggregate metrics

Rows/hour, unique-flight yield, tail-chain yield, stability, complete bucket count, ambiguity bounds, duration censoring, and cleanup/reconciliation fields are written to the durable probe row.

## Step 22 — mark completed or failed

A probe becomes `completed` only when the live-window result, metrics, reconciliation, and cleanup contract pass. Otherwise it is marked failed/censored and an incident may be opened.

## Step 23 — audit completion

We inspect the durable row, provider state, transient runtime state, raw blob refs, supervisor terminal state, and reconciliation/cleanup evidence.

## Step 24 — safely close the immutable budget day

A completed safe probe's exact budget day is closed. It is not reused for the next airport.

# 13. What the Stage-1 metrics mean mathematically

## 13.1 `rows_delivered`

Count of usable delivered notification/item observations counted by the live-window metrics. This is not automatically equal to unique flights because one flight may generate multiple observations.

## 13.2 `unique_flights`

The durable completed row stores the confirmed unique lower-bound count as the nominal unique-flight count. Identity uncertainty is separately represented by lower/upper bounds.

## 13.3 `rows_per_hour`

```text
rows_per_hour = rows_delivered / actual_window_hours
```

The Stage-2 promotion code uses a capacity gate of `60` rows/hour. Capacity is a gate, not just another score component.

## 13.4 per-credit yield

The safe-mode scientific denominator comes from the live-window internal send-credit evidence after successful reconciliation.

```text
unique_flights_per_credit = confirmed_unique_lower / credit_denominator

tail_chain_links_per_credit = tail_chain_links / credit_denominator
```

These measure information yield per paid Alert-credit activity rather than simply raw volume.

## 13.5 complete 15-minute stability buckets

Only complete aligned 15-minute intervals fully contained in the actual live window are used. If fewer than the runtime's required minimum exist, stability is null/insufficient.

For the bucket counts `x1 ... xn`:

```text
mean = average(bucket counts)
variance = average((xi - mean)^2)
CV = sqrt(variance) / mean
stability = 1 / (1 + CV)
```

Interpretation:

- perfectly even counts → `CV=0` → stability `1`;
- very uneven/bursty counts → larger CV → stability moves toward `0`.

This is why “we received many events” is not enough. We also care whether coverage exists throughout the two-hour window rather than arriving in one short burst.

## 13.6 ambiguity lower/upper bounds

`confirmed_unique_lower` counts identities we can defend as confirmed. `confirmed_plus_ambiguous_upper` represents a conservative upper bound if ambiguous identity cases were all distinct. Promotion later requires final top-five membership to remain invariant under these bounds; otherwise it refuses with insufficient identity resolution instead of pretending the rank is certain.

## 13.7 `duration_censored`

`false` means the intended full observation window completed. `true` means the run ended early, so its empirical rate/stability result is not equivalent to a full target-duration sample.

# 14. WSSS failure — detailed forensic interpretation

## 14.1 What is directly proven

The first paid Stage-1 attempt started WSSS around `2026-09-16T11:05Z`.

Early health checks showed:

- supervisor alive;
- heartbeat fresh;
- zero incidents;
- one probing row;
- active runtime session;

- zero foreign billable subscriptions;
- callback reachable.

Durable raw provider blobs were persisted between:

- first: `2026-09-16T11:11:51.272Z`;
- last: `2026-09-16T11:14:19.053Z`.

Then the health checker observed the supervisor dead, heartbeat stale, probe still logically probing, callback reachable, and provider/runtime inconsistency. Later process checks confirmed the original supervisor/owner PIDs were gone.

The final WSSS durable scientific outcome remained:

- probe ID `1`;
- `status='failed'`;
- `duration_censored=true`;
- stop reason `supervisor_child_exit_before_runtime_session`;
- reconciliation `UNRESOLVED`;
- three durable raw blob refs;
- zero active billable subscriptions after containment;
- zero active prepaid runtime rows after containment.

## 14.2 What is strongly suggestive but not proven as the exact trigger

The prepaid runtime tables are PostgreSQL `UNLOGGED`. Those tables can be truncated/reset during database crash recovery/restart. Later database lifecycle evidence showed a PostgreSQL start at `2026-09-16T11:30:50.667Z`, which demonstrates database lifecycle churn occurred later, but it does **not** prove that the exact 11:14 failure was caused by that same restart event.

The original supervisor also used a weaker background/nohup arrangement than the repaired detached-session design. Therefore a terminal/process-group lifecycle issue was also a plausible weakness.

## 14.3 What we cannot honestly claim

We cannot say:

- “you definitely clicked something and killed it”;
- “closing the shell definitely caused it”;
- “PostgreSQL definitely restarted at the exact failure moment”;
- “the provider itself definitely caused it.”

Those claims are not proven by the evidence.

The correct conclusion is narrower: **the first implementation did not have enough durable ownership/process resilience against the failure mode that occurred.** We repaired that exact vulnerability class and OMAA then completed successfully.

# 15. WSSS repair — why it fixed the exposed weakness

The repaired path does four important things:

1. **Durable session binding before provider creation.** The random session UUID now survives loss of UNLOGGED runtime state because it is also attached to the durable probe row.
2. **Deterministic exact callback ownership.** Recovery can map the durable UUID to `/prepaid/<uuid>` and only accept a provider subscription that exactly matches billing type, subject type, ICAO, subscriber type, and callback.
3. **Ambiguity means refusal.** Zero or multiple exact matches do not trigger guess-based deletion.
4. **Detached supervisor.** The supervisor is spawned in a separate OS session/process group, reducing vulnerability to ordinary interactive-terminal lifecycle events.

Offline verification at `f06820486ca8395edde2de29a6da81f5b1dc8b40` included the GitHub V3.9 Offline Safety run `35092265247` / run number `449` = SUCCESS and local focused tests 4 files / 28 tests PASS.

# 16. Why WSSS is not simply rerun now

The Stage-1 owner treats `completed`, `failed`, and `abandoned` as terminal. WSSS therefore counts as a completed *attempt state* even though it is not a successful scientific candidate.

Why this matters scientifically: if we simply reran every failed primary until it eventually passed, failures would disappear from the selection process and the design would become outcome-adaptive.

The frozen rule is:

```text
finish all 12 primary attempts to a terminal state
        ↓
score the valid completed primary candidates
        ↓
if fewer than 5 valid primary candidates exist
        ↓
consume the already-frozen replacement sequence, one by one
```

A separate WSSS repeat could be designed later as a new explicitly labeled repeat/sensitivity experiment, but it must not overwrite the original WSSS failure or secretly replace its primary outcome.

The runner is:

- **not cron**;
- **not Replit AI Agent**;
- **not a deployment**;
- **not a checkout/pull of the helper commit**;
- **not a second provider owner**.

It is simply a one-shot `nohup` shell process that sleeps until fixed UTC times and calls the **already-audited existing f068 scripts** in the same sequence the human would have executed manually.

```text

↓
prepare/verify .replit.dev callback
↓
wait until AUTH start
↓
run fresh paid preflight
↓
if preflight != PASS_READY_FOR_PAID_STAGE1 → STOP, no launch
↓
compute exact preflight SHA
↓
call existing guarded launcher once
↓
wait briefly
↓
run existing read-only unattended-health checker
↓
if health is bad → report BLOCKED / DO NOT RELAUNCH
↓
if health is good → leave the existing supervisor alone to finish
```

The whole-workspace boundary remains: if Replit destroys the entire development workspace/container, the waiting process can disappear. The correct failure in that case is “nothing launches,” not “bypass the checks.”

# 24. Why hashes are everywhere

A SHA-256 is a fingerprint of exact bytes. If one byte changes, the fingerprint changes with overwhelming probability.

The system uses hashes so that statements like “I approved the AUTH” mean:

```text
I approved THESE exact bytes
not a file with the same filename
not a later edited file
not a recreated file that looks similar
```

Hash chain examples:

- preprobe file SHA fixes the shortlist/replacement/time-class artifact;
- runtime SHA fixes the exact per-attempt runtime/budget-day rules;
- AUTH SHA fixes scope/time/ceiling/cleanup ownership;
- preflight SHA fixes the fresh state admission result used for launch;
- execution HEAD fixes the code version expected by the callback/preflight/launcher.

This is why pulling even a documentation-only/helper commit into the live workspace **before MMUN** would change HEAD and cause the preflight/launcher to refuse. The refusal is a feature.

# 26. Supervisor, heartbeat, callback watchdog, and health checker

These are different mechanisms:

## Supervisor

Owns the paid Stage-1 child process, writes status, emits heartbeat, and triggers recovery on abnormal child exit.

## Heartbeat

A file refreshed during the live run. The read-only health checker considers a heartbeat stale if it is older than its allowed threshold.

## Callback watchdog

The supervisor checks the public `.replit.dev` callback every 15 seconds. Three consecutive failures trigger fail-closed termination/recovery rather than pretending data collection is still healthy.

## `v39_phase2g_stage1_sleep_check_v39.ts`

A separate read-only snapshot check. Healthy requires, among other things:

- supervisor process alive;
- supervisor state `RUNNING`;
- heartbeat `RUNNING` and ≤90 seconds old;
- exact AUTH/head/budget-day match;
- zero callback watchdog failures;
- nonempty persistent log;
- zero unresolved incidents;
- exactly one probing row;
- exactly one active runtime session in state `active`;
- provider subscription bound;
- exact owned CreditBased subscription active;
- zero foreign active billable subscriptions;
- callback reachable.

If any check fails it says `BLOCKED_DO_NOT_RELAUNCH`. That phrase is intentional: a failure is not permission to start a second paid copy.

# 34. Stage 1 explained from first principles — what we are actually trying to learn

This section is the conceptual explanation that was missing from the earlier version of this guide.

## 34.1 Stage 1 is an airport-selection experiment, not the final data collection

The larger V3.9 project eventually needs a **small core set of anchor airports** for the later collection design. An anchor airport is not selected just because it is famous, large, or subjectively “good.” It has to be useful under the actual AeroDataBox collection mechanism and under our fixed research rules.

That is why Gate 2 has two stages:

```text
frozen candidate list
        ↓
STAGE 1
standardized 2-hour measurements on 12 primary HUB candidates
        ↓
compare scientifically valid candidates
        ↓
select the top five under the frozen scoring rule
        ↓
STAGE 2
longer 4-hour confirmation probes on the final-five candidates
        ↓
final anchor pool only after confirmation
```

So a Stage-1 probe is closer to a **controlled measurement/calibration experiment for one candidate airport** than to “collect as much flight data as possible.”

## 34.2 Why exactly 12 airports and why the order was frozen before seeing results

The binding Plan requires exactly 12 primary candidates, all of them:

```text
HUB tier
+ in the frozen frame
+ PRE eligible
+ POST eligible
```

WSSS and OMAA had to be included, and the remaining candidates plus an ordered replacement list were frozen before paid Stage 1. The point is to prevent this behavior:

```text
observe that Airport A looks weak
→ quietly drop it
→ choose a more promising Airport B
→ report only the successful candidates
```

That would bias the experiment. The frozen order means failures count as real outcomes instead of disappearing from history.

## 34.3 What is held constant so airports are meaningfully comparable

A comparison is useful only if the main measurement conditions are standardized. Stage 1 therefore keeps the important protocol rules fixed:

- target duration = 2 hours;
- matched frozen time class and weekday class;
- same provider subscription type/path;
- same callback/storage path;
- same identity rules;
- same 500-credit probe-day protection;
- same stability definition;
- same capacity gate;
- same reconciliation/cleanup requirements;
- same scoring formula and normalization rules.

The airport changes. The measurement protocol does not get redesigned after each result.

## 34.4 What comes in during the two-hour live window

A provider subscription is created for the one frozen candidate airport. AeroDataBox then sends Flight Alert webhook notifications during the exposure window.

Conceptually:

```text
provider SEND
    ↓
our /prepaid/<runtime-session-id> callback
    ↓
raw provider bytes saved through bounded App Storage
    ↓
notification/item runtime bookkeeping
    ↓
canonical flight identity / tail-chain interpretation
    ↓
scientific aggregate metrics
```

One provider item is **not automatically one unique flight**. A flight can generate multiple updates. That is why Stage 1 does not rank airports merely by raw row count.

## 34.5 The four main scientific questions one Stage-1 probe answers

### Question A — Is there enough usable activity?

Measured primarily through:

```text
rows_per_hour
```

The capacity gate is `rows_per_hour ≥ 60`. If an airport cannot clear the capacity gate, it is not eligible to win merely because another score component looks good.

### Question B — How many distinct flights do we learn about per paid credit?

Measured through:

```text
unique_flights_per_credit
= confirmed_unique_lower / reconciled credit denominator
```

This is better than raw rows/credit because repeated updates for the same flight should not make an airport look artificially more informative.

### Question C — How much same-aircraft chain information do we obtain per credit?

Measured through:

```text
tail_chain_links_per_credit
```

This matters because the research plan cares about delay propagation across successive legs of the same aircraft. An airport producing many unrelated updates may be less useful for that purpose than one producing richer aircraft-chain continuity.

### Question D — Is the information stream reasonably distributed through the window, or is it one short burst?

Measured with 15-minute complete buckets and:

```text
stability = 1 / (1 + CV)
```

A value closer to 1 means the bucket counts are more even. A lower value means the stream is more variable/bursty. This protects against treating “one huge five-minute burst” as equivalent to reliable coverage throughout the two hours.

## 34.6 Why rows/hour and the yield metrics are different

Consider two hypothetical airports:

```text
Airport A:
300 delivered rows
but only 40 unique flights
many repeated updates

Airport B:
220 delivered rows
but 90 unique flights
more distinct flight coverage
```

Airport A has more rows. Airport B may provide more distinct flight information for the cost. That is exactly why Stage 1 records both capacity and yield rather than collapsing everything into one count.

## 34.7 What OMAA actually taught us

OMAA is our first complete example of what a Stage-1 measurement looks like.

During its full two-hour window it produced:

```text

70 confirmed unique flights
1 tail-chain link
118.493 rows/hour
7 complete stability buckets
stability = 0.451686...
reconciliation = MATCH
duration_censored = false
```

Its observed yield calculations were:

```text
70 / 237 ≈ 0.29536 unique flights per credit
1 / 237  ≈ 0.004219 tail-chain links per credit
```

Interpretation:

- it cleared the 60 rows/hour feasibility gate;
- it completed the full intended window;
- its identity bounds were clean (`70` lower and `70` upper);
- its provider/internal accounting reconciled;
- cleanup succeeded;
- therefore it became `PASS_PROMOTION_VALID`.

What this **does not** mean is “OMAA is definitely one of the final five.” We cannot know that until the remaining Stage-1 candidates have been measured and the frozen ranking/promotion procedure runs.

## 34.8 What WSSS taught us even though it is not a valid yield measurement

WSSS did not complete a scientifically comparable two-hour observation window, so its partial stream must not be treated as if it were a normal Stage-1 result.

But WSSS still gave useful engineering evidence:

So WSSS contributes **failure/reliability evidence**, not a valid completed airport-yield score.

## 34.9 How Stage-1 measurements eventually affect the anchor score

The frozen anchor score is:

```text
anchor_score =
  0.40 * traffic_score
+ 0.20 * geo_score
+ 0.20 * carrier_score
+ 0.20 * yield_score

where

yield_score = (uf_std + chain_std + stability_std) / 3
```

This is important: **80% of the score comes from exogenous reference information frozen before Stage 1. Only 20% comes from the observed Stage-1 yield measurements.**

That prevents a single unusually lucky two-hour probe from completely dominating candidate selection.

The standardized yield component uses the frozen yield-reference rule. WSSS is the preferred reference if it is valid; because the current WSSS attempt is invalid, valid OMAA is the fallback reference. If both references were invalid, the protocol would refuse scoring rather than invent a reference.

## 34.10 Why the capacity gate happens before ranking

An airport may have attractive exogenous traffic/geography/carrier characteristics but still be impractical for the provider collection path.

Therefore:

```text
completed result
        ↓
capacity gate rows/hour ≥ 60 ?
        ├─ NO → not a valid promotion candidate
        └─ YES
             ↓
        compute/fill frozen score components
             ↓
        rank later with other valid candidates
```

Capacity is deliberately a **feasibility gate**, not a bonus score.

## 34.11 What happens only after all 12 primary outcomes are terminal

We do not rank halfway through and then stop when five attractive candidates appear.

The intended order is:

```text
all 12 primaries become terminal
        ↓
identify completed scientifically valid candidates
        ↓
apply capacity gate
        ↓
normalize yield with valid WSSS or fallback OMAA
        ↓
compute frozen anchor scores
        ↓
check identity-bound ranking invariance
        ↓
if fewer than five valid primaries exist:
    consume the frozen replacement list sequentially
        ↓
select final Stage-1 top five
        ↓
STOP / handoff
        ↓
separate human authorization for Stage 2
```

This is why Stage 1 takes many days even though OMAA already succeeded.

## 34.12 Stage 2 is confirmation, not a continuation of the same authorization

Stage 2 uses target 4-hour confirmation probes on the promoted set. It exists because a single two-hour Stage-1 measurement may be noisy or atypical.

A candidate is not part of the final anchor pool merely because it ranked in the provisional Stage-1 top five. It has to survive the required Stage-2 confirmation rules, and Stage 2 needs a new authorization chain.

## 34.13 Exactly what gets saved from one successful probe

There are three evidence layers:

```text
A. raw provider content
   → App Storage objects under bounded retention

B. live working state
   → UNLOGGED prepaid session/delivery/item rows
   → intentionally cleaned after the attempt

C. durable scientific/audit result
   → logged adb_anchor_probe + budget/evidence records
```

The durable result is what lets us later say:

```text
which airport was measured
when it was measured
how long it ran
whether it was censored
how many rows arrived
how many confirmed unique flights existed
how many tail-chain links existed
what the per-credit yields were
what stability was
what the identity bounds were
whether accounting reconciled
whether cleanup succeeded
which runtime/AUTH/preprobe/code hashes governed the attempt
```

So yes: **the Stage-1 experimental result is saved even though transient runtime rows are intentionally deleted after safe completion.**

## 34.14 What Stage 1 is not measuring yet

Stage 1 is not yet asking whether the final machine-learning model predicts delays well. It is not the protected Month-1 evaluation and it is not the final Phase-6 dataset.

It is answering a narrower prerequisite question:

> Which candidate HUB airports give us sufficiently high-capacity, cost-efficient, chain-useful, stable, technically safe provider data to justify becoming the core anchor airports for the larger experiment?

That is the purpose of the work we are doing right now.
