## 2. Why prerequisite P is currently BLOCKED

The binding Plan requires prerequisite P to verify **every affected content class and every relevant retention surface**, including expiry behavior across the primary database, backup/PITR, replicas, object storage and logs. A primary-row deletion is not enough if the same plaintext provider content remains reconstructable elsewhere.

### 2.1 Owner-provided Replit database evidence

On 2026-09-11, the project owner read the production Replit Database settings panel and reported:

- Point-in-time recovery: **`On · last 7 days`**
- Recovery window: **`7 Days`**
- Therefore the current PITR recovery window used for safety analysis is **168 hours**.

This is project-specific control-plane evidence. It is more relevant to this deployment than a generic Replit product default.

### 2.2 Owner-provided AeroDataBox RapidAPI Ultra retention evidence

The project owner supplied the following plan/account retention rules:

| Content class | Owner-provided maximum / rule | Current treatment |
| --- | ---: | --- |
| Raw API payload + webhook delivery | **7 days maximum** | Hard retention class; provider plaintext must not remain recoverable after the allowed age. |
| Live FIDS query cache | **24 hours maximum** | Separate hard retention class; must not share the generic 1–7 day raw TTL knob. |
| Genuine Derived Works / analytics | **up to 365 days** | Applicable only after this exact output is proven non-trivial and non-reconstructable; normalization/copying alone is not enough. |
| Project-owned metadata/audit logs | **indefinite** | Only if the retained values contain no third-party provider content. |

### 2.3 Public-provider cross-check — what is and is not independently proven

Public AeroDataBox Terms currently support the following general rules:

- ordinary API **Contents** include raw data plus copies/extracts/reformatting;
- Article 5.5 uses a default cache/storage rule based on 7 days, Cache-Control `max-age`, or an explicitly longer Plan-Term allowance;
- genuine **Derived Works** require non-trivial processing and non-reconstructability of individual source values;
- Article 5.6 treats genuine Derived Works separately from the Article 5.5 ordinary-cache rule.

Public September 2026 material also discusses a **24-hour FIDS query range** for certain plans. That public 24-hour statement is a request/query-range capability, **not independent public proof of this project's 24-hour RapidAPI Ultra retention limit**. The 24-hour FIDS retention maximum in this report is therefore recorded as **owner/account-plan evidence**, not mis-cited as the public query-range statement.

Provider references used for this distinction:

- `https://aerodatabox.com/terms/`
- `https://aerodatabox.com/2026-09-terms-update`
- `https://aerodatabox.com/pricing/`

### 2.4 PITR consequence

With the confirmed 168-hour recovery window, plaintext deleted from the primary database at its contractual maximum may remain reconstructable from an older recovery point.

Current conservative calculation:

| Class | Primary maximum currently contemplated | Replit plaintext-recoverable PITR | Possible recoverable age | Verdict |
| --- | ---: | ---: | ---: | --- |
| Raw provider content | 168 h | 168 h | **336 h** | **BLOCKED** vs 168 h hard maximum |
| Live FIDS cache | 24 h | 168 h | **192 h** | **BLOCKED** vs 24 h hard maximum |

This is why P cannot be marked PASS merely because migration 0048 can null primary-row payloads.

The safe options must be proven before paid provider-content persistence, for example: a recovery surface whose plaintext lifetime is compatible with the hard limit, a shortened primary TTL that compensates for a verified shorter recovery window, or a design where expired plaintext is not recoverable from PITR (for example correctly designed crypto-shredding with keys outside the recovery surface). No such alternative is declared PASS yet.

These commits are real Git history. They are not, by themselves, proof that prerequisite P passes.

### 3.2 Remaining implementation defects found by audit

1. **One TTL cannot represent both rules.** The current expiry owner uses one `V39_RAW_PROVIDER_RETENTION_DAYS` setting bounded to 1–7 days. FIDS requires its own 24-hour class under the owner-provided plan evidence.
2. **Payload deletion is not full content deletion.** Several tables flatten provider values into ordinary columns in addition to keeping raw JSON. Nulling only the raw JSON can leave reconstructable provider Contents behind.
3. **Some table-level `derived_work` classifications are too broad.** A table containing copied timestamps/status/position/milestone values cannot be made a Derived Work merely by naming the whole table `derived_work`.
4. **Backup/PITR was previously not modeled as a recoverability window.** The verifier must reject a primary TTL that still leaves plaintext recoverable through PITR past the hard maximum.
5. **Replica/object/log surfaces are not yet fully verified.** Unknown affected surfaces remain fail-closed.
6. **Provider-response redaction audit is incomplete.** Any remaining raw response text in balance/refill/subscription errors must be removed before P closure.
7. **Configuration registry drift exists.** Runtime DB role keys used by the actual code must also be explicit in the no-hidden-configuration registry.
8. **P must protect callers, not rely only on human ordering.** Paid/provider-persisting callers should fail closed on current P evidence so an incorrectly issued authorization cannot bypass P.
