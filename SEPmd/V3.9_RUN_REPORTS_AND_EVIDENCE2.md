## 1. Mental model: what Phase, Gate, Stage, Probe, AUTH, Runtime, and Handoff mean

These words refer to different layers and were the main source of confusion.

| Term | Meaning in this project | Example |
|---|---|---|
| **Phase** | A large project block with a different purpose and risk level. | Phase 0 builds/verifies code; Phase 1 verifies the account; Phase 2 proves readiness and performs Gate-2 probes. |
| **Gate** | A pass/fail admission checkpoint inside the phase sequence. A later action cannot legally/scientifically proceed until its owning predecessor passes. | Gate 0 verifies account/budget; Gate 1 verifies coverage; Gate 2 is the anchor-probe protocol. |
| **Stage** | A sub-experiment inside a gate. Gate 2 contains Stage 1 and Stage 2. | Stage 1 evaluates the frozen candidate set; Stage 2 is a later confirmation step for the promoted set. |
| **Probe** | One bounded live provider experiment for one airport under one immutable budget day. | OMAA's 120-minute Stage-1 probe on 2026-09-16. |
| **AUTH** | Human-approved, exact, hash-bound permission for a specific paid action envelope. It is not the API key. | `AUTH-20260917-P2G04`, Stage-1 only, max 500 Alert credits. |
| **Runtime artifact** | Frozen machine-readable parameters for the specific Gate-2 run: budget-day ID, reservation, margin, stability requirements, predecessor bindings. | `phase2g-gate2-runtime-P2G-S1-20260917-03.json`. |
| **Budget day** | One immutable accounting envelope for one probe attempt. It is not simply “today's calendar date.” | `P2G-S1-20260916-02` for the successful OMAA attempt. |
| **Handoff** | Cryptographic evidence that one step passed and the next step is allowed to be prepared. A handoff is not automatically an authorization for the next paid action. | Phase-2F smoke handoff allows Phase-2G preparation; Stage-1 promotion handoff will be required before Stage 2. |
| **Terminal** | A probe will not be silently rerun in-place. `completed`, `failed`, and `abandoned` are terminal outcomes. | WSSS remains `failed` and is not rewritten to PASS. |

The safety idea is simple: every paid experiment is preceded by frozen inputs, exact authorization, a fresh preflight, one launch, explicit cleanup/reconciliation, then immutable evidence.

## 13. The WSSS repair — what code changed and why

The failure exposed a narrow but important ownership/recovery gap.

### 13.1 Root problem

The prepaid runtime tables are intentionally `UNLOGGED`. PostgreSQL may clear UNLOGGED contents during crash recovery/restart. The first implementation kept the random runtime-session UUID only in that transient runtime state until too late in the live-window lifecycle. If those rows disappeared, automatic recovery lost its durable bridge from the logged probe to the exact provider subscription callback.

### 13.2 Repair

The repaired design now:

- creates/binds the random Stage-1 runtime-session UUID durably in `clean.adb_anchor_probe.runtime_session_id` **before** provider subscription creation;
- retains only the random session UUID durably — not provider subscription IDs or raw provider payloads in logged PostgreSQL;
- can reconstruct exact ownership after an UNLOGGED reset only when exactly one active CreditBased FlightByAirportIcao WebHook subscription matches the exact probe ICAO and exact deterministic `/prepaid/<session-uuid>` callback;
- refuses on zero/ambiguous matches rather than bulk-deleting;
- runs the supervisor in a detached OS session/process group instead of a simple terminal background process;
- preserves every abnormal run as FAIL/UNRESOLVED;
- adds regression tests for the failure/recovery contract.

### 13.3 Verified repair state

Final repair code head used for the successful second attempt:

- `f06820486ca8395edde2de29a6da81f5b1dc8b40`;

## 15. What data is saved versus intentionally transient

This distinction matters because after OMAA completed, the runtime delivery/item tables correctly showed zero rows.

### Long-lived/durable evidence

The project keeps the scientific/audit information needed later, including:

- the durable `clean.adb_anchor_probe` result row and aggregate metrics;
- immutable statuses such as WSSS `failed` and OMAA `completed`;
- runtime-session UUID linkage needed for audit/recovery;
- reconciliation status and cleanup-verification time;
- budget-day state/evidence;
- hash-bound runtime/AUTH/preflight/run artifacts;
- provider blob references and hashes for the bounded retention interval;
- run/supervisor logs and evidence receipts.

### Intentionally transient state

The prepaid session/delivery/item runtime tables are `UNLOGGED` and are not the long-term scientific result store. After a successful probe reconciles and cleanup is verified, those runtime rows are removed. Seeing runtime counts return to zero after OMAA was therefore **expected success behavior**, not data loss.

### Provider raw-content retention

Raw provider-content blobs are stored through the separate App Storage boundary under the Phase-2 retention contract. The callback/runtime health evidence used a `168`-hour retention setting. The durable research result is therefore not “keep every raw provider byte forever”; it is “retain raw/provider evidence for the permitted bounded period while permanently retaining the project-owned aggregate/hash/audit result needed to reproduce and defend the experiment.”

## 18. Can the early-morning run be automated without changing the science?

### 18.1 Replit AI Agent route

The current ChatGPT↔Replit integration does **not** expose an arbitrary future terminal-execution capability where ChatGPT can wake at 5:30 AM, take over the Replit shell, run the exact Stage-1 scripts, and hold a live two-hour process. Replit Agent can inspect or modify an app, but using it to redesign/schedule the runner would modify the repository/runtime and would have to be re-audited before the paid experiment.

Therefore the current safe design should **not** depend on “ChatGPT talks to Replit Agent at 5:30 AM and Agent runs shell commands.”

### 18.2 Pre-sleep waiting-runner route

A safer option is possible with the existing frozen code: before sleeping, the operator can start **one fail-closed local shell process** which waits until the AUTH start, verifies the workspace callback, creates a fresh paid preflight, checks that its exact status is `PASS_READY_FOR_PAID_STAGE1`, and only then feeds that fresh hash-bound receipt to the existing detached launcher.

This can preserve the same scientific time class because the actual provider launch still happens in the required morning window. It does not require the human to be awake at launch time.

However, it does **not** solve the whole-workspace failure boundary. The Mac should remain plugged in/awake with network and the Replit workspace active. If the workspace/container disappears overnight, the waiting process can disappear. The design must fail closed — in that situation the correct outcome is **no launch**, not an unguarded retry.

### 18.3 Why no new committed scheduler is being inserted before P2G04

P2G04 was reviewed and prepared against execution head `f06820486ca8395edde2de29a6da81f5b1dc8b40`. Adding a new executable scheduler to GitHub and pulling it into Replit now would change HEAD immediately before an already-frozen paid run. That is unnecessary risk.

For the current MMUN attempt, use the existing f068 owners and, if desired, a temporary/untracked pre-sleep wrapper around them. After MMUN is terminal and its budget day is closed, a reusable audited scheduler can be added before freezing the next runtime/AUTH.

## 21. How Stage-1 completion and promotion are different

A single probe can successfully complete but Stage 1 can still be incomplete.

For an individual candidate such as OMAA, the successful path requires completed status, usable metrics, reconciliation MATCH, verified cleanup, and durable aggregate fields. OMAA passed those checks and also passed the current promotion-candidate validity checks.

The **Stage-1 sequence** does not finalize until the frozen primary membership reaches the terminal-state requirements. Only then does the promotion logic rank/evaluate the valid candidates and, if necessary, walk the already-frozen replacement list. The official promotion handoff is a separate artifact.

Therefore:

```text
OMAA = successful Stage-1 candidate

but

Stage 1 overall ≠ complete yet
Stage-1 promotion handoff ≠ recorded yet
Stage 2 ≠ authorized
```

## 27. Short glossary

| Term | Plain technical meaning |
|---|---|
| **Fail closed** | If a required fact cannot be proven, refuse the action instead of guessing/continuing. |
| **Hash / SHA-256** | Fingerprint of exact file bytes. If bytes change, the hash changes. Used to prove the reviewed artifact is the one later executed. |
| **Immutable evidence** | Historical result that is not edited to look better after later repairs. |
| **Reconciliation MATCH** | Provider-observed credit delta and internal counted send credits agree under the defined settlement rule. |
| **Duration censored** | The intended observation window ended early, so the rate/stability result cannot be treated as a full intended window. |
| **Stability bucket** | A 15-minute interval used to check whether delivery volume is sufficiently distributed through the live window rather than concentrated in one burst. |
| **Identity ambiguity bounds** | Lower/upper unique-flight counts used so uncertain matches do not silently become exact identities. |
| **UNLOGGED table** | PostgreSQL table whose contents are intentionally not WAL-logged and can be cleared after crash recovery; useful for transient provider runtime state, unsafe as the only durable ownership evidence. |
| **Provider blob ref** | Durable project metadata pointing to bounded-retention provider-content storage, with hashes/timestamps; not the same thing as keeping plaintext raw payloads in logged PostgreSQL. |
| **Promotion-valid** | Candidate passes the current individual scientific checks needed to be eligible for later Stage-1 ranking/promotion. Does not mean the whole Stage-1 sequence is finished. |
| **Consumed AUTH** | Authorization already used for its paid attempt; it is never reused for a new attempt even if its wall-clock expiry has not passed. |
