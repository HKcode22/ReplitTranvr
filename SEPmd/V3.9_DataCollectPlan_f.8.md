## 3. Budget & accounting (two budgets — Gate 0)

### 3.1 Two separate pools, one shared quota (the Gate-0 fix)

AeroDataBox exposes **two billable use paths** relevant here—REST/API-unit
requests and Flight-Alert-credit notifications. Their account relationship,
limits, and refill behavior depend on the verified channel and plan; they are
never assumed from a quota size. The 60,000-unit entitlement is user-confirmed;
the subscription channel and current account mechanics are Gate-0 evidence:

- **API quota** (units) — monthly allowance on the marketplace/subscribed plan, spent by REST calls. Under the currently pinned public provider contract, the airport FIDS endpoint is **TIER 2** and the current public pricing maps Tier 2 to **2 API units/request**. Costs for every other endpoint, variable-rate operation, retry, or account-specific plan are **not inherited from legacy estimates**: Gate 0 must freeze the current provider/account evidence and the seven-category REST ledger before billable use. Managed by the verified marketplace/provider subscription terms; entitlement renews according to the verified billing cycle.

**Billing-cycle and budget-day alignment:** The project safety cap is **1,900 Alert credits per Phase-6 `budget_day_id`**, where `budget_day_id=run_day_index` for one parent batch-day. It is not a provider calendar-day rule or a billing-cycle reset. Every SEND is attributed to the immutable owning subscription/batch even if delivery/settlement occurs after UTC midnight; store provider send/attempt date separately. The next batch-day cannot start until the prior budget day is closed and settled under §11.1, with its owned subscriptions deleted or confirmed inactive. Do not delete the budget-day ledger itself: it is an audit record. Billing-cycle boundaries affect only monthly API-unit entitlement. `MONTHLY_PLAN_ENTITLEMENT_UNITS=60,000` is user-confirmed; Gate 0 verifies the active plan/channel, cycle dates, remaining/used units, and account limits. A renewal never expands the frozen Phase-6 Alert ceiling without re-FREEZE.

`subscription_channel` is a required frozen identity, not a label inferred from
the API hostname or quota size. Gate 0 records the exact channel (for example
`RapidAPI`, `API.Market`, `direct`, or a named custom agreement), account/plan
identifier, cycle, and terms. API units, direct non-expiring API credits, and
Flight-Alert credits are separate resources; no balance or rate limit may be
borrowed across channels or ledgers. If the channel or plan terms cannot be
identified, all billable paths remain BLOCKED.

The `cycle_entitlement_units (=60,000)` line in the API tree applies only when
Gate 0 confirms that the actual subscribed channel exposes the user-confirmed
60,000-unit monthly entitlement. If the verified channel uses a different
quota, a non-expiring direct allocation, or another contract, record that
channel-specific entitlement and its units/expiry rules explicitly; do not
silently substitute 60,000 or mix it with the Alert ledger. Until that mapping
is confirmed and reconciled, the API tree and every billable path remain
BLOCKED.

**Run start date freeze:** The run start date MUST be frozen at FREEZE (before Phase 6 begins). Record `phase6_start_date` in manifest. Once frozen, the start date CANNOT be changed without re-running the entire FREEZE process. The start date determines: (a) billing cycle alignment, (b) weather archive coverage, (c) historical store bootstrap period, (d) evaluation cutoff dates. If the start date is delayed (e.g., Gate 0.5 fails), the FREEZE must be re-run with the new start date.
- **Flight-Alert credit balance** (credits) — dedicated balance, does not

### 4.2 Macro-region mapping (binding)

Use the following six macro-regions; an ICAO-first-letter heuristic alone is insufficient:

1. **North America** (NA) — US, Canada, Mexico, the Caribbean, all ISO-defined Central American countries, and Greenland.
2. **Europe** (EU) — the explicit European country-code rows in the frozen mapping artifact, plus Turkey and Russian airports whose frozen reference longitude is `<60.000000°E`.
3. **Asia-Pacific** (AP) — the explicit East/South/Southeast/Central-Asian country-code rows in the artifact, **excluding Australia/NZ/Pacific islands** (those → OC) and the explicit Middle-East rows (those → MEA).
4. **Gulf/Africa** (MEA) — the explicit Middle-East and African country-code rows in the artifact. ICAO prefix examples (`O,H,F,D,G`) are QA hints only, not a complete classification rule.
5. **South America** (SA) — the explicit ISO-defined South-American country-code rows in the artifact; Central America is not included.
6. **Oceania** (OC) — Australia, New Zealand, and the explicit Pacific-island country-code rows in the artifact. A primary-frame airport maps to exactly one region; an unresolved airport stays `UNMAPPED` and is excluded rather than forced into a region.

Missing/invalid country is `UNMAPPED`; an ICAO-prefix fallback is forbidden unless a separately versioned prefix table is explicitly frozen before Stage 1. |

### 4.4 PRE vs POST airport eligibility (binding)

**Decision (Option B — separate eligibility, explicit):**

- **PRE (provider-observable prediction population, S1):** requires `pre_eligible=true` (`feed_schedule` available) — an airport can only contribute `flight_population` / `flight_snapshots` at T-24h/T-6h/T-90m if schedule feed exists for that horizon.

- `PRE horizons never depend on an airport lacking required FIDS/schedule coverage` — controller refuses to schedule a T-24h snapshot for an airport where FIDS `withCargo/withPrivate` scope cannot be validated.

## 5. The provider-observable prediction population (S1)

**Why it exists:** the webhook is an event stream, not a complete population
enumeration. "These flights
emitted an update we captured" ≠ "these are all the flights that existed at the
cutoff." Observability selects on airport size, activity, disruption severity,
tracking quality, airline, region, ADS-B coverage — the very things we predict.

**Naming (Gate-0 fix):** the FIDS/schedule layer is called the
**"provider-observable prediction population"**, NOT a "true census". It is
"population relative to the validated AeroDataBox-supported operational frame."
**Gate 5** validates provider-population → reference operational source (e.g.,
FAA/BTS-derived schedules/ops for US flights, where available) → observed.

| Layer | Contents | Source |
| ---- | ---- | ---- |
| `flight_population` | append-only **population-observation membership** for a canonical flight instance returned by a particular role-aware FIDS query/retrieval. Logical uniqueness includes `population_query_id` (or source airport + service interval + retrieval identity), `flight_instance_id`, and `population_role`; repeated horizon/as-of retrievals never overwrite one another. For a prediction cutoff, use the latest qualifying observation whose durable `available_at≤prediction_cutoff_utc`; preserve `fids_retrieval_utc` separately and record staleness. | AeroDataBox FIDS/schedule for every planned airport+service interval; public tier/cost is only a candidate until re-verified and frozen for the actual account at Gate 0 |

### 5.2 T−24h operational acquisition (binding)

It is **forbidden** to reconstruct T−24h from a final schedule observed later. T−24h is `selected_t_milestone − 24h`; that milestone remains BLOCKED until Gate 0.5 selects a constructible provider-native schedule field under §6.0. No FAA gate/runway alias fallback is permitted. Proven in two permitted ways:

**Preferred — live, versioned schedule-population snapshots:**
```text
future airport/window assignment FROZEN early enough to schedule the longest-horizon acquisition grid
  → for T-24h, materialize a pre-frozen query-time grid spanning the service-window cutoff interval
  → for T-6h, materialize the analogous pre-frozen query-time grid
  → for T-90m, materialize the analogous pre-frozen query-time grid
  → each query starts early by population_acquisition_guard and covers the frozen service interval (split only by verified provider range)
  → experimental webhook window (collection)
  → later outcomes
```
A request started exactly at a cutoff does **not** prove its response was usable by that cutoff. Before Phase 6, Gate 0.5 must MEASURE→FREEZE: (a) `population_acquisition_guard_minutes` from FIDS latency + scheduler/queue/rate-limit allowance + explicit safety margin, (b) `population_refresh_cadence_minutes`, and (c) `population_max_staleness_minutes`. For each horizon `H`, materialize a **non-adaptive retrieval grid** whose target cutoff span runs from `service_window_start_utc − H` through `service_window_end_utc − H`; each grid request starts at least the frozen guard before its target grid instant. Each retrieval covers the same frozen service interval (subject only to verified range splitting), so later-in-window flights can use a fresher pre-cutoff population observation rather than being judged only from the earliest flight's snapshot.

The actual membership rule remains decisive: for each flight/horizon select the **latest** qualifying population observation with durable `available_at ≤ prediction_cutoff_utc`; record `population_observed_at_utc` and `population_staleness_seconds`. If no qualifying observation exists, or if its staleness exceeds the frozen `population_max_staleness_minutes`, mark that flight/horizon `population_unobserved`/ineligible for the primary denominator rather than assuming absence. A slow response whose durable `available_at` crosses the flight cutoff is not eligible for that flight/horizon. A later FIDS query can never backfill an earlier cutoff and **can never backfill an earlier population** membership decision. The refresh cadence/guard/grid is frozen and budgeted before Phase 6 and may not adapt to outcomes, yield, or disruptions. `assignment_frozen_at` must be early enough to schedule the full guarded T−24h grid; otherwise that horizon is unavailable rather than reconstructed from future state.

### 5.3 FIDS timezone / DST handling (binding)

Provider FIDS `fromLocal/toLocal` bounds are **airport-local time**. Fixed `UTC±offset` is forbidden.

```
canonical UTC experimental interval (e.g. window_start UTC, cutoff UTC)
  → airport IANA timezone (from airport metadata, e.g. America/Los_Angeles for KLAX)
  → convert to local date/time with DST-aware library (e.g. `Intl` / `date-fns-tz`)
  → correct fromLocal/toLocal strings (e.g. "2026-08-30T08:00")
  → provider query
  → persist original fromLocal/toLocal + IANA timezone + UTC equivalents (both)

```

### 5.4 REST/FIDS materialized-calendar budget proof


### 6.1 Dual prediction-state data contract (PRE + AIRBORNE)

The plan has **two distinct prediction states**, never merged into one row.
**An event is NOT one of them.** `prediction_state` is a property of the
**snapshot / training example**, derived at dataset-construction time; the raw
 event carries only immutable provider/source facts (`event_phase`, canonical
source clocks, `timestamp_source`, `data_stage PRE|POST`); optional semantic
`event_timestamp` may be NULL. The same observation may feed
features for multiple tasks → we never burn an event's reusability by stamping
it with one state. The two derived states:

```text
prediction_state = PRE_DEPARTURE        cutoffs: T-24h / T-6h / T-90m
                                        valid under frozen provider-native PRE criterion
                                        target: gate-out delay / arrival disruption /
                                                cancellation / diversion

prediction_state = AIRBORNE             state_observation_time_utc = provider location/state time
                                        prediction_cutoff_utc = deployable decision/as-of time,
                                        normally this item's `available_at` after durable ingestion
                                        valid only under independently verified provider-native airborne
                                        movement evidence; otherwise denominator BLOCKED
                                        target: landing ETA, remaining time from prediction_cutoff_utc,
                                                selected-primary delay, P(selected_primary_delay>15/60), diversion risk
```

**The cutoff rule is universal:** for BOTH states, a feature may enter only when its **information availability** is no later than the deployable decision cutoff. PRE uses the frozen T−24h/T−6h/T−90m decision cutoff. AIRBORNE stores two times that must never be conflated: `state_observation_time_utc` (when the aircraft state/location applies) and `prediction_cutoff_utc` (when our system can actually make the prediction, normally that observation item's `available_at`). The current observation is therefore eligible for its own AIRBORNE snapshot without pretending the system knew it before receipt. Source latency is `prediction_cutoff_utc − state_observation_time_utc`. Actual departure may be used only if its information was available by the AIRBORNE decision cutoff; actual arrival remains a future label.

**Availability-time rule (NEW, blocking — the deepest leakage fix):** "the
event happened before the cutoff" is NOT sufficient. A model predicts from
what the **system could actually know at the decision time**, so the eligible
condition is:

```text
feature eligible  iff  information_available_timestamp ≤ prediction_cutoff
```

where `information_available_timestamp` = when OUR system had the value (the
time a downstream feature could actually be built from it). This is stricter
than `event_timestamp ≤ prediction_cutoff`, which only proves the thing
happened, not that we knew it. Every preserved observation carries provider-native
timestamps and they are NEVER conflated:

```text
provider_notification_generated_utc  when the provider generated the notification
provider_state_updated_utc          when the provider's internal state was last updated
location_reported_utc               when the location was reported (nullable for non-location events)
http_received_at_utc                when our HTTP layer received the raw delivery
raw_persisted_at_utc                when raw envelope was persisted (BEFORE 2xx)
available_at                        when our ingestion made it usable for feature-building
```

Example that must NOT leak: `location_reported_utc = 14:00`, `provider_state_updated_utc =
14:01`, `http_received_at_utc = 14:06`, `raw_persisted_at_utc = 14:06:01`, `available_at = 14:07`. With a
prediction cutoff of 14:05 the observation is INELIGIBLE even though
`reportedAtUtc ≤ 14:05`, because `available_at = 14:07 > 14:05`. This
discipline applies uniformly to: flight events, FIDS/schedule revisions, live
flight status, weather observations & forecasts (TAF amendments),
network/congestion features, and tail/rotation features (previous-leg arrival
must be both landed AND its arrival value available, by cutoff). For a source fact, `available_at` is the earliest time the fact was durably usable by the system. For a deterministic derived feature, preserve three clocks: `input_knowledge_available_at=max(required_input.available_at)`, `online_feature_available_at` when an already-deployed transform actually made the feature usable (nullable for offline replay), and `materialized_at` for the later table build. Eligibility requires every input to pass the cutoff and the exact transform version to have been frozen/deployable by the cutoff; an online feature additionally requires `online_feature_available_at≤cutoff`. Offline replay may use the frozen transform over cutoff-eligible inputs, but later materialization never changes what was knowable. No availability clock is backfilled from a final dataset.

### 7.5 Route / OD and aircraft/tail identity (binding)

**Route/OD identity:** `directed OD = (origin ICAO, original_scheduled_destination ICAO)` — ordered pair, directed. Keep `original_scheduled_destination`, `operational_destination`, and `actual_destination` separately; diversion is `actual ≠ original` plus `diversion_flag`. The next origin must equal the prior operational destination (or scheduled destination only under the frozen no-diversion rule).

**AIRBORNE / POST population denominator (NEW, blocking — the POST-side
population audit, mirroring §5):** "flights with airborne events we happened to observe"
is NOT a defined population. The **`airborne_eligible` denominator is
population-defined independent of airborne observation capture** — it comes
from the SAME `flight_population` layer as PRE (§5: provider-observable FIDS
population), intersected with **verified provider-native movement evidence** that
the flight became airborne. Permitted evidence is a FIDS operational state whose semantics are verified to imply departure, or a provider-native departure `runwayTime` only after **both runway semantics and actual-vs-estimated status** are verified. Estimated runway time cannot establish that the flight actually became airborne. A webhook point cannot define this
denominator. If neither independent criterion is constructible,
`AIRBORNE_DENOMINATOR=BLOCKED`. A flight is
`airborne_eligible` whether or not a single airborne point was ever captured —
using the airborne webhook to define the denominator would make it circular
with `airborne_observed`. Every eligible flight then goes through the same
measured funnel as PRE does, and each stage is counted and reported:

```text
airborne_eligible        = flight_population (FIDS-observable, §5)
                           ∩ verified_airborne_movement_evidence
                           [denominator defined from FIDS/population evidence,
                            NOT from whether we captured airborne points]
airborne_observed            ≥1 airborne observation captured for that flight
airborne_usable              ≥ N usable points (N frozen in manifest;
                             proposal ≥ 2 to fit a line, ≥ 5 to fit a curve)
airborne_trajectory_complete passes trajectory-completeness threshold
                             (completeness_% / max_gap_seconds, §6.2 QC)
POST_snapshot_eligible       produced ≥1 POST training snapshot (cutoff rule §6.1)
POST_labeled                 received a final terminal label (§6.2 terminalization)
```

- **Report the funnel at every monthly checkpoint:** `eligible → observed →
  usable → complete → snapshot_eligible → labeled`, e.g. as
  `airborne_eligible → airborne_observed → … → POST_labeled` proportions and
  per-airport / per-tier rows, exactly like the PRE population funnel (§5).
- **Missingness is measured, not hidden:** `airborne_eligible − airborne_observed`
  quantifies provider coverage; `observed − usable` quantifies point quality;
  `complete − snapshot_eligible` quantifies cutoff/cadence losses. If a big
  step collapses (e.g. most flights observed but few complete), that's a
  provider-cadence finding (Gate 0.5 / monthly), and POST training is weighted
  to the funnel denominators — a POST model must NOT be silently trained only
  on the easy-to-track tail of flights (`airborne_observed` disproportionately
  on provider-friendly aircraft/routes).
- POST-only rows from airports/feeds without independently constructible FIDS population membership are `POST_auxiliary=true`. They may support descriptive/auxiliary modeling but never denominator-based population claims.

### 8.6 Coverage floor (no-starvation) (binding)

Mathematically, every eligible REGIONAL airport requires `traffic_prior_i>0` and `m_i≥0.25`; otherwise frame validation fails. Define `adaptive_score_i=traffic_prior_i·m_i` after the §8.2 zero-yield rule. If the airport has no qualifying Phase-6 direct observation or its last qualifying observation is ≥20 days old, set `coverage_floor_eligible=true` and `coverage_boost_i=1.5`; otherwise set `coverage_boost_i=1.0`. At every draw compute `draw_score_i=adaptive_score_i·coverage_boost_i` and `p_i=draw_score_i/Σdraw_score`. An unsuccessful draw does not clear eligibility. Only a successful valid Phase-6 direct observation resets coverage age/boost. The boost never overwrites `m_i` and remains an efficiency/coverage preference, not a representation claim.

**Coverage clarification:** positive probability—even with a boost—does not guarantee finite-run selection. If many/all airports are overdue, a common multiplier may not materially change normalized probabilities. Report floor eligibility, effective boosted score/probability, coverage age, and realized selection frequency separately; never call this deterministic starvation prevention.

**Adaptive determinism:** `m_i`, zero-yield state, eligibility, boost, scores,
and probabilities must be deterministic from the same frozen configuration and
history. EMA uses fixed `α=0.5`; clamp/penalty/boost rules contain no random
branch. Only the final weighted draw uses the frozen random seed. Replay the

### 9.2 Yield-reference normalization (binding)

The old word **"calibration"** for anchor yield is renamed **"yield-reference normalization"** to distinguish from probabilistic model calibration (ECE/Brier in §13.1).

- **Primary reference:** WSSS (Singapore Changi) — `reference_yield_wsss` measured with the identical target-2h, 500-cap-censored protocol.
- **Fallback reference:** OMAA (Abu Dhabi) — used only if WSSS `capacity_gate` fails or WSSS probe invalid; `reference_yield_omaa`.
- **Diagnostic:** Both probed even when one is primary; report `wsss_vs_omaa_ratio`.
- **Invalid-reference behavior:** If both references fail capacity gate → probe aborts, manifest records `reference_invalid`, no scoring.

**Yield standardization formula (binding):**

```text
component_std = clamp(candidate_component / reference_component, 0, 1)
where candidate_component ∈ {uf_per_credit, chain_per_credit, stability}
      reference_component = reference_yield_wsss.component (or omaa if fallback)
      clamp(x,0,1) = min(1, max(0, x))
```

Each required `reference_component` must be finite and strictly positive. Use
the OMAA component only when the corresponding WSSS component is invalid and
the pre-frozen fallback rule permits it. If both are missing, non-finite, or
zero, that component—and therefore anchor scoring—is `NOT_SCORABLE`; Gate 2
remains incomplete. Never divide by zero, insert an after-the-fact epsilon, or
drop/reweight a component after seeing candidate results.

Clipping justification: values above reference saturate at 1.0 — intentional, because anchor yield is a **minority 20% component** of `anchor_score`; saturation prevents a single lucky probe from dominating (see §8 anchor score).

**Anchor score (binding, frozen):**
```text
anchor_score = 0.40·traffic_score + 0.20·geo_score + 0.20·carrier_score + 0.20·yield_score
yield_score  = (uf_std + chain_std + stability_std) / 3
traffic_score = per §4.5 exogenous traffic normalized
geo_score, carrier_score per §4.5
```
Station/API capacity is a **feasibility gate** before scoring, never a score component.

**Stability calculation (binding, exposure-correct under cap censoring):**
```text
bucket_width = 15 minutes
use only complete 15-minute buckets fully contained in the actual active probe interval
count_i = distinct canonical flight instances whose first valid observation in this probe falls in bucket i
n_buckets = number of complete observed buckets
mean = Σcount_i / n_buckets
variance = Σ(count_i - mean)² / n_buckets   # population variance across observed buckets
SD = sqrt(variance)
CV = SD / mean   (if mean=0 → stability=0)
stability = 1 / (1 + CV)
```
Retries/updates never recount a flight. An unobserved portion after a cap stop is **not** filled with zero buckets. Freeze `min_stability_buckets` before paid probes; fewer complete buckets yields `INSUFFICIENT_SAMPLE` for stability rather than a fabricated score. The final partial bucket is excluded unless an explicit exposure-normalized rule is frozen before Stage 1.

`SETTLEMENT_UNRESOLVED` and blocks further paid work; do
not extend exposure or declare PASS. The smoke measures the actual delayed-send
behavior and freezes `unsettled_burst_margin_credits` for Stage 1/2 as at least

decrease it. Later charges that appear after an earlier record reopen that

1. **Exclusivity (R1):** list subs; delete/disable every non-experimental
   **active** subscription; verify no foreign sub **capable of billable
   delivery** remains (inactive/historical records can't bill → not
   contamination).
2. `balance_before` + timestamp (in audit chain).

The canary cost is **not** assumed to be one credit; AeroDataBox bills each flight item sent, and a busy-airport notification can contain multiple items.

The provider can still settle sends after local deletion, so the reservation/margin and settlement steps remain mandatory.
5. **Settle:** apply the shared settlement rule above. Let `B_stable` be the
   final value only after at least three consecutive equal authoritative reads
   across the frozen stability window; two adjacent equal reads alone are not
   sufficient.
6. `C_external = B_before − B_stable`.
7. `C_internal = Σ notification_items(received)` from the immutable ledger.
8. Composition: notifications (POST count), items/notification, max burst,
   stored/inserted/updated/skipped, delivery_failures.
9. **PASS iff** `|C_external − C_internal| = 0`, all applicable received
   `deliveryAttempt.costCredits` reconcile with item counts, failures=0,

If later operational bursts demonstrate unavoidable discrepancy, create a separate `PRODUCTION_RECONCILE_TOLERANCE` with measured evidence. Do not reuse the failed one-credit historical run as calibration for tolerance.
10. SOFT_STOP margin is tuned from this canary's measured burst and then
    frozen before the next paid run; it is not retroactively applied to the
    canary.

**Notification balance vs final accounting:** `C_external = B_before - B_stable` measures credits consumed by **webhook notifications only** (the Alert subscription). This is NOT the same as the final accounting for the entire run, which includes: (a) webhook notification credits (measured by canary), (b) FIDS REST API units (measured by per-category ledger in §5.4), (c) any supplementary REST calls (measured separately). The canary proves webhook accounting correctness; the per-category ledger proves REST accounting correctness. Do not conflate these two accounting systems.

### 11.3 Webhook reliability & the budget-day cap (R2 — Gate 4)

- `maxDeliveryRetries = 0`; delivery failure → **PAUSE** the run, stop the
  batch (`stop_reason='delivery_failure'`), **flag** affected rows/observations
  (`sampling_reason='delivery_failure'` or audit column), log "reconcile before
  resume". Never silently resume.
- **Failure window:** The time between provider SEND/delivery failure and operator detection is unbounded. Population+horizon eligible flights still receive snapshot rows; notification-derived features are missing and independently flagged `missing_notification`. They are not silently removed from the denominator. Log `failure_window_start`/`failure_window_end`; never infer the window is bounded by the next batch.
- `SOFT_STOP = 1900 − ADB_DAILY_SOFT_STOP_MARGIN` (50 is only the proposal until frozen) stops the active
  batch when its `budget_day_id` ledger reaches it; `HARD_CAP = 1900`; overshoot →
  `reconciliation_status='MISMATCH'`.

**Hard-cap safety mechanism:** If `HARD_CAP = 1900` is exceeded:
0. Safety decisions combine authoritative balance polling, received `deliveryAttempt.costCredits`, the durable internal ledger, and the frozen `unsettled_burst_margin_credits`. Because billing occurs on SEND, a charged delivery that never reaches or persists at the webhook still counts. Received-item count alone is never the cap watchdog.
1. The intended watchdog immediately stops the active batch.
2. The overshoot batch is flagged `reconciliation_status='MISMATCH'`.
3. **Compensating control, not erasure:** after a settled budget-day overshoot, reduce the next scheduled budget day's authorization by the overshoot (`next_budget_day_cap=max(0,1900−overshoot_amount)`) and recompute the run remainder. This does not undo the deviation or prove it cannot recur.
4. **NEW:** If overshoot > 100 credits, the run is PAUSED and requires operator intervention before resuming.
5. Log `hard_cap_overshoot` with owning budget day, amount, timestamp, attribution evidence, and next-budget-day adjustment in the actual batch/evidence schema.
6. Do NOT silently absorb overshoot into the daily budget without logging.
- **Status:** repository behavior is not established by this Plan. The complete SEND-aware watchdog, failure injection, and scaled Gate-4 path are `NOT_VERIFIED` until current production-caller and integration evidence closes them. This is mandatory offline work, not a scope exemption.
- Production batch-start logic **must** perform orphan/foreign-subscription cleanup/exclusivity checks at every batch start; implementation status is proven only in the Log.
- Second-start protection permits at most one parent batch per `run_day_index` and refuses any new batch while a prior budget day is unsettled.

### 12.2 Feature discipline

- **Universal eligibility rule (NEW, blocking):**
  `information_available_timestamp ≤ prediction_cutoff` — a feature is
  eligible only when our system could actually have KNOWN it by the cutoff,
  not merely when the event says it happened (§6.1). Notification generation,
  delivery attempt, provider state update, nullable location report, HTTP receipt,
  durable persistence, and `available_at` are preserved separately. A generic
  feature timestamp is never a substitute for the information-availability
  clock; it may be retained only as a derived diagnostic with its provenance.
- **Schedule/status/destination as-known-at-cutoff (NEW, blocking):** a PRE
  snapshot may use **only the version of the schedule that was observable by
  its prediction cutoff**. `scheduled_/revised_departure_utc(at_cutoff)`,
  `scheduled_/revised_arrival_utc(at_cutoff)`, `destination_at_cutoff`
  (original vs current vs actual) are each stamped with the time the value
  became known. The final/revised value that surfaced AFTER the cutoff is a
  LABEL or test-time input only — never a snapshot feature. Same discipline
  applies to AIRBORNE snapshots (use state observable at observation
  timestamp t). Rationale: an airline revising departure 15:00→16:00 at 13:00
  must NOT leak into a T-6h, 09:00-cutoff training example built later from the
  current FIDS value — that leakage makes an otherwise clean dataset look
  artificially strong.
- Tail/rotation features: previous-leg counts only if landed before cutoff
  AND the previous leg's arrival value was **available** by cutoff
  (`information_available_timestamp ≤ prediction_cutoff`, §6.1). Knowledge
  status is stored per previous leg: `previous_leg_exists_known`,
  `previous_leg_landed_known_0/1`, `previous_leg_arrival_value_known_0/1`,
  `previous_leg_arrival_available_at`. "Landed but value not yet in our system
  at cutoff" is treated as UNKNOWN, exactly like a landed-but-unreceived event.
- Explicit missingness features: `tail_known`, `days_since_last_obs`,
  capture flags — never silently dropped.
- **As-of historical feature store (NEW, first-class, blocking):** features
  like recent airport/route/tail delay, congestion, utilization and
  operational state need a historical lookback that a 31-batch-day collection does
  NOT automatically provide at T-24h/T-6h/T-90m. These get an explicit immutable
  store, `historical_feature_store`, keyed by `(airport|route|carrier×airport|
  tail|OD-pair|weather) × datetime`, where EVERY row carries:
  `feature_value, source, source_timestamp, information_available_timestamp,
  valid_from, valid_to`. A snapshot at time T builds its feature by fetching
  the most-recent value with `information_available_timestamp ≤ T` — never by
  computing it later "from the completed dataset", which would be
  retrospective leakage (§6.1). The store is populated during the run (and by
  the §10 archive layers for weather), not reconstructed after.

**Historical store source matrix:** The historical store must document the source for each feature type:

| Feature type | Effective/source time | Information available timestamp | Notes |
| ---- | ---- | ---- | ---- |
| Airport/route recent **actual delay** | Verified actual movement milestone time for each contributing flight | max of contributing source facts' `available_at` plus deterministic aggregate transform | `fids_retrieval_utc` is retrieval/provenance time, **not** the flight's effective event time. Until actual milestone semantics are verified, recent-actual-delay features remain NULL/unverified. |
| Tail utilization / previous-leg state | Verified movement milestone(s) of the prior legs | max required input `available_at` | Requires stable tail identity; cross-midnight allowed. |
| Congestion/count state | Service/movement interval being summarized | max required FIDS/event `available_at` | Preserve retrieval time separately. |
| Weather METAR | `observation_time` | actual source retrieval/availability time | Observation time alone does not prove our system had it. |
| Weather TAF | `valid_time` + `issue/amendment_time` | actual retrieval/availability time | Latest amendment allowed only if issued **and available** by cutoff. |
| GFS/NAM | `valid_time` separate from `model_run/issue_time` | actual release/retrieval `available_at` | Never use forecast valid time as issue time. |
| ERA5 | reanalysis valid time | exact product release/retrieval `available_at`, if verifiable | Otherwise retrospective diagnostic/truth only; not an operational as-known feature. |
| ATC program | source-defined program effective time | source retrieval/availability time | Optional; named source/field required. |
| Storm/radar | source observation/valid time | source retrieval/availability time | Optional; named NOAA product required. |

Record `source_matrix_version` in manifest. Verify source availability at Gate 0.5.
- **Warm-up / bootstrap rule (NEW, blocking):** Day 1 of collection CANNOT
  build T-24h/T-6h historical features from data that only starts on Day 1 —
  the store must be populated BEFORE the first eligible prediction snapshot.
  Define a **pre-run bootstrap period** (weather backfill from §10 archives +
  provider/FIDS state history as far back as the provider retains, plus any
  qualifying pre-run collection) so that the earliest evaluation day has the
  same historical as-of maturity as later days:
  ```text
  PRE-RUN BOOTSTRAP (weather archive backfill + history as deep as provider retains)
       ↓
  historical_feature_store populated; availability frozen (history_ready_at)
       ↓
  Day-1 evaluation begins — first prediction cutoff is AFTER history_ready_at
  ```
  The global `history_ready_at` prevents structurally immature early days from entering the preregistered primary evaluation. After that global readiness point, row-level missing historical inputs **do not delete an otherwise population+horizon-eligible snapshot**: values remain NULL with `history_incomplete=true` and the frozen model missingness strategy handles them. Report a `history_complete` sensitivity subset separately rather than selecting the primary denominator on post-hoc feature completeness.
- **Hard consequence for Model −1 (persistence):** `airport recent delay`,
  `route recent delay`, `previous-leg delay` are its core inputs. Without the
  bootstrap, the first portion of the dataset is structurally different from
  the rest and Model −1 is not even well-defined. The bootstrap is therefore a
  pre-implementation requirement, not a nicety.
- **No `1/p` auto-weight.**

### 12.2.2 Chain completeness (binding)

Chain completeness uses **nested denominators**, never one row counted as two denominators:

| Category | Definition | Role |
| ---- | ---- | ---- |
| `scheduled_candidate_successor` | Tail has a chronological next scheduled departure from the previous destination within `max_turnaround=6h` (cross-midnight rotations allowed), excluding known chain breaks | Denominator for scheduled coverage |
| `observable_candidate_successor` | A scheduled candidate whose successor interval is actually observable under the frozen collection/population design | Subset of scheduled candidates; denominator for primary link-rate |
| `successor_linked` | Observable candidate matched to a confirmed/provisionally bounded flight identity under the identity rule | Numerator |
| `known_absent` | Evidence the expected continuation does not exist / operation terminated | Classified separately; excluded under the frozen candidate rule |
| `unknown/boundary` | Successor lies outside observable support | Not an observable-candidate failure |
| `aircraft_swap` / `missing_registration` / conflict | Chain break or un-linkable identity | Excluded from link denominator and reported separately |

Report at minimum `scheduled_chain_coverage = observable_candidate_successors / scheduled_candidate_successors` and **primary** `observable_chain_link_rate = linked_successors / observable_candidate_successors`. Optionally report `scheduled_chain_link_rate = linked_successors / scheduled_candidate_successors`, explicitly noting that it combines observation coverage and linkage. Never treat an unobservable future leg as a link failure.

### 12.3 Graph edge taxonomy

- **Static** (route/schedule, from catalog + schedule ref data)
- **Dynamic** (state-at-T congestion, from snapshot columns at cutoff)
- **Resource** (capacity/ops: runway/stand/ATC config, from reference + flags)
- **Aircraft/flight-chain** (same-tail legs — first-class edge type for delay
  propagation)
- **Missing edge ≠ zero edge:** `known-absent` (observed, no edge) vs
  `unknown` (unobserved) are distinct masks; a GNN that treats "not observed"
  as "no edge" learns the collection pattern, not aviation structure.

**Graph edge → collection requirements (each edge must be constructible from
preserved fields):**
- *Static route:* flight_population (dep/arr ICAO pairs from FIDS/schedule).
- *Dynamic congestion:* flight_snapshots + flight_events state-at-T (airport
  delay aggregates at cutoff).
- *Resource:* reference/event flags (runway/stand/ATC config preserved on the
  event row).
- *Aircraft/flight-chain:* aircraft_reg-joined same-tail leg sequence from
  flight_events — explicit gate-out → wheels-off → wheels-on → gate-in chain
  per tail, as an event history (SDSU chained-prediction support, §19).

## 14. Marginal value per credit (the final objective)

**Two quantities, never conflated:**
- **Feature contribution:** `ΔM_feature = M(full) − M(without feature)` on
  held-out tests (ablation — modeling result, NOT a budget result).
- **Collection marginal value:** `MV_data = ΔM / Δcredits` from **real
  collection interventions** (+1 obs-day WSSS vs +1 MID vs +1 REGIONAL vs +1
  tail-chain vs +1 week on an existing hub), `Δcredits` = actual cost.
   Only genuinely randomized treatments may be called "randomized/paired";
   other comparisons are observational/paired-observational/exploratory.

**Marginal-value claims clarification:** The marginal-value claims must be precise:
1. **MV is per-credit, not per-flight:** `MV = ΔM / Δcredits`, NOT `ΔM / Δflights`. Credits and flights are not 1:1 (different airports have different costs).
2. **MV is relative, not absolute:** MV measures improvement from adding data, not the absolute value of the model. A high MV means data is scarce; a low MV means data is abundant.
3. **MV is context-dependent:** MV varies by airport tier, region, time-of-day, and disruption frequency. Report MV separately for each context. Do NOT claim a single universal MV.
4. **MV is paired, not observational:** For genuinely randomized interventions (crossover §8.7), MV is measured from paired comparisons. For non-randomized interventions (+1 MID, +1 REGIONAL, +1 WSSS day, +1 week), MV is observational/paired-observational/exploratory — label accordingly.
5. **MV may be negative:** Observed out-of-sample `ΔM/Δcredits` may be negative (adding data can hurt generalization, e.g., distribution shift). Allow and report negative estimates with uncertainty bounds. Do NOT claim MV is bounded below by 0.

**Learning curves (two axes; never equate credits with rows):**
- **Cost-indexed checkpoints:** Alert-credit checkpoints may use cumulative 2k / 5k / 10k / 20k / 30k / 40k / 50k and the **actual frozen Phase-6 Alert ceiling** when reached. REST API units are reported alongside Alert credits; the two resources are never silently summed or converted.
- **Sample-indexed checkpoints:** freeze model-specific sample checkpoints before the first fit from the attainable realized domain (`N_PRE_snapshots` for PRE; `N_POST_snapshots`/`N_airborne_points` for POST; `N_unique_flights` always reported). Do not assume 58k credits = 58k flights or observations.
- Fit `metric = a·n⁻ᵇ + c` only where the chosen sample-size `n` was actually observed; extrapolation is labeled "predicted, unmeasured" with uncertainty.

**Learning-curve sample-size definition:** Every curve records `N_unique_flights`, `N_PRE_snapshots`, `N_POST_snapshots`, `N_airborne_points`, `Alert_credits`, and `REST_API_units`. A flight at T-24h and T-6h contributes two PRE snapshots but one unique flight. Cost claims are reported as the resource vector `(Alert_credits, REST_API_units)` unless a future explicit valuation/conversion rule is separately frozen; never add the two billing units as if they were identical.
