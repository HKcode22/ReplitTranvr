# P09/P18 — actual localhost fixed incoming HTTP URL with crash-visible source spool and backup receiver replay

Prepared Saturday October 10, 2026 Pacific, isolated draft PR #27. **ZERO paid AeroDataBox calls/credits, ZERO live database reads or writes, ZERO hosted/deployed/public endpoint, ZERO Cloudflare/extra Replit accounts, ZERO main merge.**

## Exact operator question / reason for this implementation

The user wants a one-main, multiple-backup receiver design for ~120-minute paid flight collection, and a prospectively approved separate-incident six primary + six emergency health-check policy (15 seconds × 12 checks = 180 seconds, with cumulative whole-run uncertainty and spend budget). **Three domain URLs alone cannot rescue a provider HTTP POST directed to exactly ONE frozen webhook URL.** Separate billable AeroDataBox subscriptions may multiply credits and break experiment source ownership; mid-run delete/recreate creates missing source windows.

To investigate without provider credits or new hosting, implemented **a real loopback-only HTTP prototype** with **one fixed incoming URL for the lifetime of its running frontdoor**, a raw-byte spool independent of *mock* backend receiver availability, and an explicitly invoked one-target-at-a-time replay operation with configurable 1–3 localhost receivers. This is not deployed independent infrastructure; the frontdoor remains a single host/service dependency.

## New source and tests

- `experiments/phase2g_rehearsal/synthetic_fixed_frontdoor_spool_v39.ts`: synthetic-only, disallows real AeroDataBox API/webhook secrets or real V39 database URL and requires `P2G_SYNTHETIC_FRONTDOOR_ONLY=YES`. Only `/tmp`-like disposable spool roots, private file permissions and loopback HTTP ports accepted. No Replit/Neon/AeroDataBox SDK import.
- Ingress authenticates with a **test-only constant-time checked token**, validates a synthetic attempt ID, limits original body to 65,536 bytes, and preserves **unaltered original wire bytes**: writes/fsyncs raw file, renames, fsyncs parent directory, writes/fsyncs exact source hash/length/attempt receipt, renames, fsyncs receipt directory. **Only after verifiable local file receipt does it return synthetic HTTP 202.** This simulates durable ordering on a single runner filesystem, NOT power-loss proof or independent cloud durability; actual AeroDataBox response handling/202 acceptance is not verified.
- An exclusive local source-claim lock prevents simultaneous same-attempt admission from acknowledging incomplete source. If the process crashes after claim but before original source/receipt, a later callback returns 503; it NEVER guesses source bytes from a hash or auto-cleans abandoned claims. If original source was admitted and the HTTP 202 was lost, re-sending the same attempt preserves the original bytes/hash and returns the same receipt; a changed original with same claimed attempt ID fails 409.
- Replay is separate/explicit (not hidden background processing). It enumerates exact source receipts, verifies all original wire bytes and checks prior immutable success marks. It forwards raw bytes only to localhost mock receivers in operator-provided priority order; if receiver 1 fails 503 or receiver 2 lies about its source SHA, it tries receiver 3. It treats a receipt as forwarded only after a backend returns 200 with matching simulated ID/sha acknowledgment and writes/fsyncs its own success marker. If the ACK or marker is lost **after backend persistence**, retry may POST twice; backend MUST deduplicate by exact attempted source/sha. It never broadcasts to multiple AeroDataBox subscriptions and never deletes raw source after replay.
- Source spool has no provider sender-attestation, no production durable queue, no real physical-flight-instance-v2 identity or 8-bin research rows; original bytes are stored on **disposable local disk**, not PostgreSQL plaintext or Replit App Storage. All vendor credits = 0 and every replay result has `paidLaunchAuthorized:false`, `originalProviderWitnessVerified:false`.
- `tests/phase2g_synthetic_fixed_frontdoor_spool_v39.test.ts` exercises: preserved whitespace/wire bytes and receipt across local spool-object re-instantiation; exact duplicate/no second upload; conflicting attempt denied; primary unavailable while standby accepts; 3 receiver priorities and lying 200 rejection; both down+later replay; lost backend ACK requiring duplicate-safe replay; corrupted raw blob fail-closed; half-written claim leaves 503 rather than false 202; unauthorized/oversized/bad-ID rejected; explicit **frontdoor itself down** means other healthy backends do not receive a new POST; 22 concurrent real loopback synthetic HTTP sends with subsequent spool drain. A final added test deliberately aborts a mid-body POST and verifies no partial-source acknowledgment and that the frontdoor stays healthy.
- CI workflow includes both source/test files in its path triggers and normal offline suite. The unchanged true disposable PostgreSQL16 integration test separately proves actual V3.9 UNLOGGED reset; the new frontdoor uses **no actual PostgreSQL** by design.

## Explicit FAIL/NO-GO and why MORE BACKUP REPLIT URLs do not cure it

1. **Frontdoor down is still a lost new sender POST** when provider `maxDeliveryRetries=0`; even three healthy standby receivers cannot observe the missed source. A truly highly available and independently durable fixed HTTPS front door must be deployed and proven outside the primary Replit failure domain before treating any backend failover as genuine.
2. **Single host filesystem is NOT an operationally independent replicated original-source journal**; fsync file/directory helps local ordering but does not establish restart/replacement availability of another host, disaster recovery, storage immutability, regulatory retention or 168h verified hard deletion. No production writes permitted to this spool.
3. **AeroDataBox unique sender attempt identity/credit unit is not independently authenticated here**: the test's `x-synthetic-attempt-id` comes from a mock sender. Exact provider retries/200/202 acceptance, source signature, plan credits and externally billed 260 vs internally 259 remain unverified.
4. The backup receiver mock's 200/receipt SHA is NOT a cryptographically authenticated signed physical-flight source custody receipt or a cross-instance published-revision/bucket parity check.
5. **Safety guards**: no new publisher/account, no Cloudflare, no paid service, no real authentication material, no live Neon/App Storage. Synthetic file fixture must be removed at test teardown. Never import this module in the live paid webhook process or use it to authorize a paid launch.

## Oct 10 P13/P16 additional local crash-recovery spool audit, and production-backup caveat

The fixed localhost frontdoor's new `auditCrashRecoveryReadOnly()` method scans a bounded number of private raw/original-receipt/claim/forward-success marker filenames, returning aggregate-only counts of verified receipts, tampered originals, absent raw sources, claim-without-receipt, raw-without-receipt, forwarded-without-source and quarantined partial temporary files. It never modifies files, deletes sources, replays, acknowledges webhooks or claims independently authenticated AeroDataBox source evidence. Additional test cases deliberately create partial-claim source loss, an original object lacking a final source receipt, a receipt lacking its original object, and a partial temporary write; verified/successful receipts are distinguished from incomplete or corrupted originals.

**Don't conflate this with hosted recovery:** a local filesystem's fsync and an accurate orphan list are insufficient to withstand a full primary hosting outage or prove retention after a cloud disk replacement. Teammate's live published `travnr.com` also is not yet a compatible V3.9 science standby: [read-only two-app Replit backup parity report](2026-10-10_P09_P18_REAL_REPLIT_PUBLISHED_BACKUP_PARITY_READONLY_CHECK.md) records the deployed physical-flight-v2 deficit, unknown secret/bucket/db equality and actual deployed revision mismatch. No network failover was enabled.

The true V3.9 server JSON parser captures raw incoming bytes in `req.rawBody` for duplicate-key structural inspection, but persistence currently serializes `canonical(input.body)` before object storage. This is **not the same as a literal original incoming HTTP wire-byte archive**. An additional direct V3.9 localhost HTTP + disposable PostgreSQL/forced fake App Storage test asserts the byte difference, to prevent unsupported claims about original-wire fidelity.
