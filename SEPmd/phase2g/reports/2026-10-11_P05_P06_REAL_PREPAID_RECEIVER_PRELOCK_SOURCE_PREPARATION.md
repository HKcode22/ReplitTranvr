# P05/P06 — actual prepaid receiver moves deterministic source preparation out of PostgreSQL session lock

**Engineering implementation, 2026-10-11 UTC**, isolated draft PR #27 on `phase2g-p2g24-github-observer-20261009`. **Source code changed in the actual V3.9 prepaid receiver implementation**, not a synthetic stand-in, but **NOT merged, NOT published, NOT authorized for paid YSSY**. No live provider requests, PostgreSQL scientific writes, deployment, Replit charges, cloud resource creation or secret access was performed. This does not assert Replit production was repaired.

## Reproducible pre-change failure and current objective

Previous real callback code `persistPrepaidProbeWebhookV39` acquired a pooled PostgreSQL connection, began an SQL transaction and locked `clean.prepaid_probe_session_runtime` with `FOR UPDATE` **before** canonically serializing the entire JSON, calculating its digest/delivery identity and canonical SHA-256 for each flight item. The same lock remains held across Replit App Storage original blob upload + download + byte readback, physical-v2 item SQL and COMMIT. This creates a sender-original response latency bottleneck. Earlier **real disposable PostgreSQL16 + actual HTTP prepaid route** artificial 22-send burst showed **17 timely original sender HTTP 200 / 22 requests** even though **22 eventually committed**, with 550ms *fake* original blob delay. It is wrong to call those simulated numbers real hosted Replit latency or a source ledger for historical 260/259.

## Change to actual callback (safe limited increment)

- `server/lib/disruption/prepaidProbeRuntime_v39.ts` now exports `preparePrepaidProbeSourceV39(sessionId, body)`, a synchronous deterministic and side-effect-free source preparation operation. It derives the canonicalized JSON **as previously stored**, raw buffer, canonical notification digest, provider notification/attempt UTC and cost fields, delivery ID, flight list and every flight's canonical item SHA-256.
- `persistPrepaidProbeWebhookV39` invokes preparation **before** `pool.connect()`, `BEGIN`, `SELECT ... FOR UPDATE`, blob upload or SQL mutation. Duplicate detection and record hash matching consume the same precomputed values. Within the physical-v2 item loop the precomputed item SHA is used; it is no longer recomputed within that long transaction.
- Importantly, this is **not a redesign of source admission**: no ACK before blob round-trip and SQL COMMIT, no switch of storage representation, source identity, provider retry, raw retention, physical identity, owner/credit limits or original F.8 scientific acceptance. If canonicalization is invalid it fails synchronously before occupying a pooled SQL connection. This is a smaller safe performance increment, not the missing independent durable first hop.
- Added **opt-in redacted** `source_prepare` timing via a new guarded synchronous `timePrepaidSyncStageV39` helper in `server/lib/disruption/phase2gPrepaidStageTelemetry_v39.ts`, allowlisted by `server/phase2gCallbackOnly.ts` only when `V39_PREPAID_STAGE_TELEMETRY=1`. It records *stage name/duration/outcome only*, never raw provider payload, flight, secret, SQL or URL; failures from telemetry listeners must never affect callbacks.
- Tests `tests/phase2g_prepaid_prelock_source_preparation_v39.test.ts` independently verify stable canonical JSON, original-body and item hashes, attempt identity isolation, empty payload behavior, refusal of invalid/circular input and source-ordering relative to `pool.connect` and `FOR UPDATE`; updated telemetry tests verify sync failure handling and no source disclosure. The entire pre-existing actual HTTP+disposable PostgreSQL integration fixture is included in CI.

## What this does NOT claim

This may reduce time occupying a PostgreSQL connection/lock, especially for a large provider JSON with many flights; **no measured production improvement or end-to-end P95/P99 effect yet**. The big overhead is still the **entire slow App Storage upload/download and physical-v2 SQL while one session row is held**, so this limited change cannot fix 10s send-deadline 22-way bursts by itself. It also cannot prevent Replit Autoscale scale-to-zero POST loss, a crash-before-original-durability, loss of PostgreSQL UNLOGGED science state, unobserved provider original notifications or external 260/internal259 unresolved credits. No new user Shell command or costly rehearsal is required for development of this draft.

## Next engineering phase, safety requirements

1. Integrate a **separately durable, crash-safe original source admission journal and replay**, so a primary process crash **after sender send but before upload** cannot fabricate a durable ACK. A LOGGED hash-only pending intent is insufficient: it cannot reconstruct absent original bytes when provider delivery retries are zero.
2. Only once original source is durably admitted: safely move slow provider object storage out of the per-session SQL `FOR UPDATE` span, with duplicated-attempt conflict/replay proof, exact LOGGED vs UNLOGGED custody, quota/TTL/orphan deletion and unknown SQL COMMIT outcomes. The existing 22-way two-phase fixture is explicitly **disposable-only** and must not simply be imported into the paid receiver.

Prove strict 10s sender-side success under concurrent live-path synthetic faults against an isolated *published-equivalent* receiver, plus real source, billing and owner attestation; isolate compute/hosting fees before any user runtime request.
