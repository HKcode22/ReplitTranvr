## Why this is the next blocker after 6+6 policy research

A watchdog that tolerates 6 primary + 6 evidence-gated emergency health checks cannot itself preserve paid incoming original webhook bytes or unblock a `POST` that waits inside the database/receiver. The actual paid callback (a) acquires a `pg` pool connection, (b) takes `SELECT ... FOR UPDATE` on **the entire prepaid session row**, (c) uploads and reads back the original provider blob **while still holding that row lock**, (d) resolves and persists physical-flight-v2 per item, (e) commits, and only then allows HTTP 200.

Earlier actual-route + disposable PostgreSQL16 tests showed two structurally opposed failure mechanisms under synthetic 18–22 concurrent callbacks with 550–600ms in-memory fake blob upload: a short 3s connection wait produces some HTTP 503/unreceived attempts, while a long wait can commit internally but respond **after the original synthetic sender's 10s deadline**. The current experimental 4s DB acquisition timeout remains **DISABLED BY DEFAULT**. Simply changing 3→6/12 failed watchdog GET checks or shifting from 3s→20s pool wait **cannot guarantee receiving the paid original POST**.

- Every stage is timed around **actual** `persistPrepaidProbeWebhookV39` code, not a separately reimplemented mock. Real tests exercise exact prepaid Express HTTP route and actual disposable PostgreSQL with simulated raw App Storage. New/duplicate source paths and SQL failures continue preserving the existing row-lock and commitment semantics. **No transaction/ACK/owner/paid policy changed by timing.**
- A private explicitly subscribed observer is used instead of Node `diagnostics_channel`: Node `diagnostics_channel` observers can throw an asynchronously fatal uncaught exception. In this implementation each listener is called in `try/catch` and cannot turn a successful callback into 5xx or kill its host. The timing operation itself treats metrics as optional and nonblocking.
- `server/phase2gCallbackOnly.ts` enables *sanitized logs* only with `V39_PREPAID_STAGE_TELEMETRY=1`, and logs only the fixed stage/outcome and milliseconds. **Default: no stage logs**, no synthetic/live owner changes. Existing P08 HTTP transport warning (server-finish/close/slow) remains separate. In neither case does server `finish` prove the real provider saw HTTP 2xx inside 10s.
- New `tests/phase2g_prepaid_stage_telemetry_v39.test.ts` tests complete and failed stage metrics, hardcoded redaction/allowlist, malformed metrics refusal and exception-isolated listeners. Actual disposable PostgreSQL integration adds two tests proving redacted stage sequences across success + duplicate readback and that a deliberately throwing telemetry subscriber **cannot** alter real durable webhook HTTP 200.
- Existing 22-notification synthetic strict-10s-sender-deadline actual-route test now captures every exact PostgreSQL session-lock duration and simulated raw-object-stage duration, computes **P50/P95/P99** for lock wait and P95 for fake blob, confirms per-message SQL COMMIT staging, and redacts secrets/session IDs.
