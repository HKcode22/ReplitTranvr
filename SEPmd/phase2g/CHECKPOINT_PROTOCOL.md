# Durable checkpoint protocol for every Phase 2G work session (2026-10-12)

**Standing project working convention:** After every substantive analysis, fix, review, release, experiment or work session, save a dated human-readable Markdown checkpoint **in GitHub**, rather than relying on chat history alone. This is documentation process only, never a paid authorization or override of the frozen Plan.

## Session start (read before modifications)
1. Read the most recent dated report in `SEPmd/phase2g/reports/`, current relevant PR and issue discussion and canonical `SEPmd/phase2g/README.md`; locate `SEPmd/V3.9_DataCollectPlan_f.8.md` and `SEPmd/V3.9_IMPLEMENTATION_LOG.md`.
2. Independently verify repo identity, exact branch/HEAD, recent CI, deployed code if relevant, frozen scientific protocol, budget/active subscription status and any pending exact AUTH. Old checkpoints are evidence, not license to infer current state.
3. Carry forward explicit user decisions and differentiations: original scientific failures vs valid runs, independent data/accounting/host reliability outcomes, zero-provider vs paid effects.
4. Triage work in **P0 safety/validity**, **P1 bounded prospective methodology**, **P2 optional reliability**, **P3 cleanup**; do not indefinitely reopen settled P0 tests over P3 theoretical issues.

## What to write at end of every session
- UTC/PDT timestamp; purpose; decision deadline.
- Repository, branch, **full commit SHA**, PR/issue number and merge/deployment status.
- Baseline scientific protocol name/hash and future proposal version if relevant; historical non-promotions.
- Work actually executed vs drafts/proposals; changed files, commits/CI IDs, test counts and precise results; failures and unsupported assumptions.
- Financial side effects: provider API calls, subscriptions, actual balance/credits from verified evidence or UNKNOWN; database mutations; provider and staging host facts.
- Current release targets, actual tested published Git SHA and verification receipt if present.
- What remains, blockers separated from non-blocking future improvements, accountable next actions and next exact **read-only** command or link.
- Safety boundaries: which actions still require explicit user's consent, paid AUTH and preflight.
- No passwords, tokens, secrets, raw provider-identifying payloads or private customer data in checkpoints.

## Storage and linking
1. Prefer `SEPmd/phase2g/reports/YYYY-MM-DD_<SUBJECT>_CHECKPOINT.md` or updating that day's existing checkpoint. Use additive entries for genuine state updates rather than creating a new file for every small conversational response.
2. If a release code tree/hash is already frozen, write to a **separate documentation branch or GitHub issue discussion**, not a surprise source change in an authorized release. Document which branch contains the checkpoint and link it from the relevant PR/issue.
3. Add forward links from the checkpoint to the current source, logs, docs and execution artifacts; make claims only from grounded evidence.
4. At the beginning of a new chat, read that latest checkpoint and verify current GitHub/live state; don't blindly replay commands involving money, database mutations, overwrites or production deployments.
5. State current position truthfully as GO/HOLD/NOT_YET_VERIFIED; never promise work was performed between chats. Deadline goals govern engineering focus, not evidence truth.

## For a deadline like YSSY Oct12 20:00 PDT
- Freeze P0 scope, stop optional research and speculative fixes, focus on reviewed source + runtime/Auth hashes, administrative historical disposition, provider headroom, matched publication/callback receipt, protected ledger approval, exact owner preflight.
- If a deadline arrives with a hard unknown, record HOLD, don't weaken/falsify approval. A local synthetic rehearsal cannot be represented as proof of published Autoscale durability.
- Post-launch: log real costs, missingness, original source custody and science promotion decision separately.
