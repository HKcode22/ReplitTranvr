# V3.9 Plan f.8 — Scientific Amendment C: source coverage over the actual 31 batch-days

**Effective for new prospective Phase 5 freeze proposals after 2026-11-07.**
**Status:** Proposed binding correction to f.8 §§5.2, 5.4 and 8.7, subject to reviewed code/tests and independent actual-source evidence. This is a *versioned scientific refinement*, not a change to what was observed in historic Phase 2G/4; it does not retroactively turn missing Gate 5 evidence into a PASS.

**Reason for changing our plan:** We are permitted to update the experiment because we authored it. Scientific constraints should be changed only transparently, with the competing options, formulas, effects on cost and selection, and test results recorded. The old Stage11 software model of 31 consecutive UTC dates × one contiguous four-hour interval **was a simplified computational assumption**, not equivalent to our f.8 experiment. Its assumption conflicts with the five required crossover pairs, 2×2h gaps, up-to-6h treatments and washout, so it cannot be used as a final FREEZE proof.

## C1. Correct experimental unit and temporal domain

Binding §8.7 remains: 31 **ordered parent batch-days** (not necessarily consecutive calendar dates): **26 × single 4h**, **3 × two exposed 2h segments with a strictly positive inactive gap**, **2 × up-to-6h planned windows**. Exact five paired crossovers (3 compare 4h vs split; 2 compare 4h vs up-to-6h), both periods same frozen airport set/UTC time class/weekday class/evaluation partition and ≥24h END→next START washout of reused airports. A period-2 replay is a repeat of the parent *treatment template's* airports, **not** a redraw. Crossover randomization unit = batch-day; clustered airline/flight observations do not become independent randomized treatment units.

For a parent batch day `d`, the flight *exposure* is the union of its half-open service segments:

`E_d = ∪_s [segment_start_utc(d,s), segment_end_utc(d,s))`.

For split 2×2h, the open gap `[segment1_end, segment2_start)` is **not in the exposed population denominator**, even though source messages or webhooks might arrive then. Such rows are tagged `captured_outside_population`, not silently included. For an up-to-six-hour plan, six hours is the *maximum planned interval*, and budget-stopped shorter actual exposures must carry their censoring and stop reason.

## C2. Correct pre-cutoff source-refresh proof for every service segment and range partition

For each `d × airport-slot (HUB/MID_A/MID_B/REGIONAL) × horizon (T−24h,T−6h,T−90m) × exposed segment × provider-range partition`, form the exact half-open cutoff interval

`I_{d,a,h,s,p} = [partition_start_utc − h, partition_end_utc − h)`.

If a provider account's **independently verified** maximum response service range is `R`, partition each exposed segment contiguously into `min(R, remaining)` service spans. **Do not** partition the parent 2×2h across its inactive gap. Every FIDS source request has its own exact source service bounds and one actual scheduled physical UTC GET time. A six-hour window must be split when the measured maximum is less than six hours; never assume an undocumented six-hour response.

Define reviewed upper bounds:
- `L_s`: scheduler/rate-limit slip;
- `L_p`: response plus durable persistence latency;
- `M`: separate pre-cutoff commit safety margin;
- `S`: allowed maximum source population staleness.

A scheduled GET `q` provides a **conservative theoretical admissible cutoff span**, **only** when `S > L_s + L_p + M`:

`C(q) = [q + L_s + L_p + M, q + S]`.

For every exposed partition, the union of all its verified planned `C(q)` intervals must continuously cover `I_{d,a,h,s,p}`. If a millisecond is uncovered, **HOLD** that group and record the first uncovered cutoff and its span. A response returned after a given flight cutoff is never used to manufacture PRE evidence; genuine per-flight selection still requires the most recent independent original with `available_at ≤ cutoff`, and the selected provider-native T remains independently authenticated.

This is a *conservative planned timing feasibility calculation*, **not** a statement the provider served the requested flight, the response was actually durable, the provider's flight identity was physical/unique or the user may legally use the data.

## C3. Source GET and REST budget accounting

Charge each **physical** FIDS GET to the **UTC date of the scheduled/requested GET**, not the batch-day's service date. That includes the T−24h day(s) preceding the first experimental window. For each refresh in a partition's query sequence, place the first service-range partition GET into `FIDS_BASE_UNITS`; additional range-partition GETs into `FIDS_SPLIT_UNITS`. With independently validated unit cost `u`:

`FIDS_BASE = u × count(partition_index = 1)`

`FIDS_SPLIT = u × count(partition_index > 1)`.

Count every distinct physical GET exactly once. A retry is a **new physical** provider call and must be reserved in the separate `FIDS_RETRY_UNIT_BUDGET` before dispatch, never concealed as free/repeated software control flow. Keep all seven separate REST categories: base, split, retry, validation, outcome, history, diagnostics. Require every UTC request date to have a full seven-key reservation row; verify day caps, seven category cycle ceilings, protected REST floor and project cap ≤50,000 independently of Alert SEND credit budget. The per-parent 1,900 Alert SEND cap applies to BOTH child segments combined; it must not be treated as 1,900 per child or as equal to any REST daily cap.

A calculated calendar/source plan can fail because the measured source-age/latency/range and budget cannot satisfy all required cutoffs. This is a valid **UNSAT** for that set of fixed assumptions, not permission to backfill, broaden a provider time range without evidence, or silently drop crossover treatment days. If a revised design is warranted, explicitly amend/freeze new treatment, estimand, cap, and power/missingness analysis before paid collection. We can redesign **prospectively** without erasing old evidence.
