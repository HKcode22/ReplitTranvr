## Exact feature and what it does

- `migrations/staged/V0077__phase4_gate5_original_fids_reservation_binding_v39.sql` creates **one small metadata-only binding table**: retained `clean.fids_query_response.population_query_id` (native UUID), V0076 irreversible original `expected_reservation_sha256`, exact `query_digest`, `manifest_sha256`, original `response_hash`, retention evidence digest and conservative use-expiry. No raw provider data, provider IDs, flight numbers, schedules, aircraft or positions are copied to the new table.
- The insertion trigger joins **actual committed** V0076 physical attempt → frozen allowed query → owner → frozen manifest and checks physical reservation timing, matching GitHub owner identity, the existing raw FIDS source row's original hash/chronology, source not expired at binding, source arrival no later than that planned query's cutoff, and a use expiry no more than seven days after original availability. The 7-day bound is conservative engineering only, **not legal authorization for any storage**; permitted purpose may end earlier.
- An update-denial trigger forbids alteration or extension of a historical binding. Retention-owner deletion is intentionally possible under *future separately granted and reviewed* privileged cleanup, to respect content expiry and right-to-erasure requirements. No default production role grants/installation or paid HTTP.
- A dedicated GitHub workflow runs only inside disposable PG16 during review and matching main pushes. It applies B0062 plus staged V0076/V0077, generates entirely **synthetic local test rows** in a rollback transaction, tests valid source hash/attempt binding, wrong-original SHA refusal, duplicate refusal, immutable update refusal and empty table after rollback. It has no external provider credentials or production connection secrets.
