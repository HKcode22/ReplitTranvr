## Plain-English GitHub Actions explanation

An Actions workflow run contains one or more *jobs*. A **job** starts one GitHub-hosted runner, installs the reviewed source, then can execute a script that loops inside the SAME running process: e.g. `await check(); await sleep(5000)`. That is distinct from a GitHub **cron schedule**, which queues a new run no more often than once every five minutes and may start late or be dropped. In one pre-armed runner, the future live script should (a) confirm signed scope, independent approved owner and clean provider account; (b) remain running before CREATE; (c) poll balance, inventory and owner evidence; (d) STOP only the positively owned exact ID when soft limit, expiry or fault arises; (e) verify strict provider absence and ≥3 stable post-STOP balances and produce immutable scientific/accounting receipt. It must **not** CREATE itself in the safety job, and cannot claim an absolute cost cap.

The [five-tick no-provider workflow](https://github.com/HKcode22/ReplitTranvr/actions/runs/39865778857) succeeded. This proves GitHub can run 5-second in-job synthetic checks; it **does not** prove a live AeroDataBox DELETE, durable provider ID binding, job survivability, approved environment secrets or live callback delivery. A runner can terminate unexpectedly. **Free GitHub Actions is an acceptable disclosed risk-managed proposed operator platform**, given the owner's limited infrastructure resources, *conditional on distinct, explicit owner approval of failure and budget risks*; the original strict Plan's provider hard-cap guarantees must be recorded as unverified, not fabricated.
