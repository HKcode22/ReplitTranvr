## 1. Root cause and diagnostic attribution

GitHub's official documentation explicitly states scheduled events can be delayed under high load, and sufficiently high load can drop queued jobs. It recommends offsetting away from the start of the hour. See https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule and https://docs.github.com/en/actions/how-tos/troubleshoot-workflows#scheduled-workflows-running-at-unexpected-times. These are platform limits; the docs do not diagnose the cause of each specific miss. We also have a design weakness: overly relying on exact cron start and several jobs sharing each five-minute tick.

Actual latest main history reread: run 44006658604 was created AND run_started_at 2026-11-17T02:57:02Z, versus inferred nominal 00:17Z, 160.03 min after the inferred slot. Its actual job receipt 133783543292 generated 160.22 min instantaneous delay, six eligible slots, zero timely, three late (137.23/138.38/160.03) and three without matching observed runs. The same equality of creation/start is seen in available SOURCE/PRE/retention examples. Delay already existed before our code ran; do not blame npm, database or AeroDataBox for those observed delays. Our observer allocates nominal slots from run creation time; there is no authoritative intended fire timestamp for a dropped or >4h delayed event, so missing means unobserved assigned slot, not individually proven platform drop. Other possible causes (workflow state, account settings, concurrency queue) not independently ruled out. Manually triggered earlier eight-runner prearm had 0–7ms local release slip; that only establishes precise waiting after runners are ready, not cron SLA or actual live Neon/provider response.

## 4. Plain-language definitions retained for the owner

- A regression is something that previously worked and breaks after a change. Regression tests check that known behavior stays correct, including safety refusal paths. Native Node regression tests use the runtime's built-in node:test rather than an extra test framework; disposable PostgreSQL tests use actual PostgreSQL in a test container, not the live database. Both are different from real provider/production evidence.
- A branch is a separate version of the same project; a pull request (PR) proposes merging its tracked changes into another branch (usually main) and provides diff, checks and review. Two PRs are normal; combining disjoint verified files in our case lets CI test their interaction and makes one eventual main/pin handoff. An integrated release candidate is the combined proposed version, not installed or activated. It may still be modified if a genuine blocker is found; earlier green checks do not apply automatically to subsequent code.
- A release manifest is a versioned list of exact software, scientific/configuration inputs and their SHA256 identifiers; file inventory is the list of tracked executable/dependency/test/etc. paths and hashes, not flights, row count, or a second database. The last 2,165 to 2,176 result meant 11 added files plus 23 modified, not 11 new databases or records. This candidate changes nine existing executable files, not new paths in that inventory. Final manifest refresh pending after actual stable review; do not call stale manifest approved.
- The repository main is the canonical integrated code branch. Production runtime is separate (Replit and existing Neon DB); a PR merge changes code identity but doesn't automatically certify database staging/paid collection. Our primary cleanup is pinned to a main commit deliberately, hence coordinated re-pin after final reviewed merge. There is no authority to make up real source rights or scientific truth from code passing.
