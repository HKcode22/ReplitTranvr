## Engineering finding: codes are not the same as operational orchestration

But the source dispatcher currently consumes a **single day** using `P5_SOURCE_BATCH_REGISTRY_FILE` + `P5_SOURCE_BATCH_RUN_DAY_INDEX`; the later-PRE batch similarly consumes a **single** `P5_LATER_PRE_BATCH_REGISTRY_FILE` + `P5_LATER_PRE_DAY_INDEX`; the POST dispatcher uses **one** future signed POST packet variable. A reviewed future-day registry must be published/prospectively pinned and selected for **each actual study day** without silently changing a frozen day. No code has yet proven dynamic 31-day rollover through all those packet types, authentic native flight enrollment and POST coverage under real authorization. That remains an engineering **P0** alongside the calendar/cost work, not proof that existing code has failed.

The correct next implementation should **reuse** all existing queue, source and POST child functions, add only the missing independent **per-day signed registry selection/continuation**, keep a bounded throughput/censor accounting, and exercise date rollover and source–T24–T6/T90–POST/STOP on disposable PG16 before production GO.
