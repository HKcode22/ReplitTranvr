# Phase 5 Stage5 correction — immutable template, real GitHub run ID prearm

**Status:** staged PG16 changes + unarmed one-query CLI; no paid source workflow, no live Replit migration, no permission grants, no Phase6 GO. This corrects a genuine operational impossibility in merged PR #422.

## Root cause

The Stage5 v1 `data-collection/phase5/frozen/*.json` design required `approvedCodeSha` to equal the **final commit SHA that includes the signed file itself**, and `githubRunId` to equal an **actual GitHub Actions run ID that does not exist until the job starts**. The frozen, committed file cannot reliably contain either future value. Manually inventing these breaks provenance and creates misleading "authorized" plans.

## Solution, without loosening source-use or budget gates

1. **Template v2:** reviewed JSON is now `v39.phase5.github-source-one-query-template.v2`; includes immutable acquisition, manifest, query, actual selected-day draw and signed provider/retention rights assertions. **No future GitHub run ID or self-referential code SHA** is permitted in its JSON; exact raw JSON hash remains verified against the independently approved SHA stored in GH trusted environment/release configuration. At runtime, source admission verifies actual GitHub repository/ref/event, `GITHUB_SHA` equal to independently approved current 40-char commit SHA, real `GITHUB_RUN_ID` syntax, first run attempt, exact rights/budget/role signoffs. It supplies the actual run ID separately.
2. **V0080 staged DB migration** `migrations/staged/V0080__phase5_bind_actual_github_run_id_before_fids_get_v39.sql`: signed allowed query is initially `PREPARED` with reserved placeholder `github_run_id='00000'` and no paid attempt. In a separate durable prospective transaction, dedicated GH source worker calls `clean.prearm_phase5_fids_github_query_v39(manifest,query,ACTUAL_GITHUB_RUN_ID,draw,rights,independently computed SHA)`. The function checks exact immutable selection+calendar/rights, trusted DB clock within a bounded owner window and signed query, locks the row and changes it to `ACTIVE` with real run ID. It inserts an immutable prearm record. A V0080 **BEFORE INSERT trigger on every V0079 paid reservation** refuses any direct attempt lacking matching **previous durable real prearm**. The trigger failure rolls back physical-request ledger and all API budget debits atomically.
3. **Updated CLI:** the Stage5 one-query source owner now takes real `GITHUB_RUN_ID` from the admitted runtime, calls V0080 prearm, checks committed prearm readback and then uses **trusted PostgreSQL clock** to wait until the exact signed physical GET time (bounded to two hours; polls every five seconds). It checks lateness and remaining source+commit cutoff margin before allowing the Stage4 adapter to make V0079 reservation and at most one paid FIDS GET. An early GitHub start cannot consume a future paid reservation; a late or stopped job cannot backfill. Failed/ambiguous prearm is not automatically retried. The immutable query JSON's exact provider request and rights remain pinned independently.
4. **Test:** new no-provider CI installs actual baseline B0062, staged V0079 and V0080 into disposable PostgreSQL16, verifies an unprearmed forged ACTIVE query cannot reserve even if the V0079 reservation function is invoked, bad prearm hash doesn't activate, valid actual run ID does activate, duplicate prearm rejected, one physical reservation charged to three budgets, immutable prearm and denied PUBLIC privileges. Pure source-admission tests verify a future run ID assigned at runtime is supported while self-referential fields in a template are refused.
