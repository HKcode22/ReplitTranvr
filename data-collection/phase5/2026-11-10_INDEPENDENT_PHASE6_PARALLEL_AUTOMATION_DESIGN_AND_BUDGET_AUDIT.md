### Learn the nouns before reading the engineering sections

| Word or phrase | Meaning in this specific AeroDataBox project |
| --- | --- |
| **GET / FIDS GET** | One paid airport/time-range API request to AeroDataBox. It can return many flight rows. No flight count should be inferred from the request count. |
| **Flight / operating leg** | One actual airline-operated flight (not a duplicate marketing codeshare or merely conditional schedule). Identity must be independently authenticated. |
| **PRE task** | One job of saving *one eligible flight at one particular prediction horizon*—T−24h, T−6h or T−90m—by its own cutoff. One flight can have three tasks, without becoming three distinct ML flights. |
| **Packet** | One small reviewed instruction about the flight/horizon, the original SOURCE evidence, its true cutoff and versions/rights. It is not the whole FIDS response or a GET. |
| **96-packet shard** | One wrapper/page of up to 96 packet instructions. For 200 tasks that means 96+96+8 entries in three pages. Ninety-six is not a data collection limit. |
| **Worker / lane** | One simultaneously active flight PRE processor; **four lanes** means at most four independent Stage14 transactions simultaneously, not four APIs or providers. |
| **Concurrency** | Work happening at the same time. Proposed tests with 1/2/4/8/16 lanes are exploratory benchmark settings, NOT measured or approved live lane counts. |
| **Latency / seconds** | Time consumed by one operation. Five seconds per flight was a **made-up example** to understand concurrency, not a measurement. |
| **p50 / p95 / p99** | Median, 95th percentile and 99th percentile latency: among 100 observations sorted fastest to slowest, p95 describes roughly the 95th ranked time. They help catch *unusually slow* operations. |
| **Three-minute PRE window** | Existing Stage14 allows a write attempt within 180 seconds before that specific flight/horizon cutoff, with a 2-second proof margin. Do not confuse with four-hour airport sampling window. |
| **Queue / D** | A database checklist that remembers which flight×horizon needs work after a GitHub job exits. Does not itself call AeroDataBox or prove a COMMIT. |
| **C / parallel** | Several workers can invoke the SAME existing Stage14 writer for different flights. We do not need a new SQL writer for each worker. |
| **Watchdog** | Independent monitor that inspects missed/stalled jobs, unknown commits, remaining money, Alert STOP; can notify/trigger only separately permitted safe recovery. A four-hour owner report is optional; 3-minute PRE windows need more frequent operational checks/prearming. |
| **Transaction** | Short SQL all-or-nothing operation: BEGIN, check, INSERT, COMMIT or ROLLBACK. No transaction should stay open while waiting 45 minutes for a flight cutoff. |
| **COMMIT_UNKNOWN** | It might have saved the row even if the network lost the answer. It must be independently checked, not blindly rerun. |
| **Atomic claim / SKIP LOCKED** | In one short database transaction, one worker takes ownership of an available queued task while skipping tasks another worker is claiming. Not an extra API request or scientific flight selection method. |
| **Lease / fence** | A short-term worker ownership and generation check; an old crashed job cannot later impersonate the new owner. |
| **Backfill** | Writing today and pretending that PRE was truly saved before yesterday's flight cutoff. This is prohibited. |
| **Native T** | The exact first scheduled departure timestamp from the permitted provider for the verified operating leg. Later schedule changes must not secretly redefine the original horizon. |
| **SOURCE class** | Type of evidence, *not an additional provider*: AeroDataBox airport FIDS original, AeroDataBox Alert callback, later AeroDataBox POST, optional separate NOAA weather. |
| **Signed policy / materialization / PK** | A previously independently approved set of rules generates private concrete flight-task instructions automatically. “Materialize” means create those reviewed task objects; “PK” means database primary key/unique row identifier. A hash is not a legal license or an approver. |
| **TTL** | Data retention duration; some original provider Contents might have seven-day caching limits, unlike certain lawfully derived metrics. Confirm exact rights and storage/backup policies before 31-day model training. |
| **Database queue vs reconciliation** | Queue says what needs work; reconciler independently checks whether an uncertain SQL write actually committed. They are not interchangeable. |

### Understand 100 tasks and why more lanes reduce the illustrative total seconds

The phrase “100 overlapping tasks” **does not say our project has already collected 100 real flights**. It is a synthetic *stress case*: pretend 100 distinct eligible operated flights each needs its T−6h observation within roughly the same three-minute period. If each Stage14 transaction + separate confirmation hypothetically takes 5 seconds, total work is **100×5 = 500 seconds**. One worker does all 500 seconds alone. Four workers share that work and could ideally finish in around **125 seconds**, with a real scheduler. Eight workers could ideally require about **65 seconds** in 13 waves of five seconds. Sixteen about **35 seconds** in 7 waves. These numbers derive from **100 tasks ÷ number of lanes**, with five seconds of assumed service time, and **ignore** real DB contention/slow starts. Workers that are waiting for a future due time DO NOT use a valuable active SQL-writing lane while waiting.

**What actually happens for one flight?** If originally scheduled at 18:00 UTC Feb 10: its T−24h cutoff is 18:00 UTC Feb 9; T−6h cutoff is 12:00 UTC Feb 10; T−90m cutoff is 16:30 UTC Feb 10. The GitHub controller prearms before each. It must have a genuine saved SOURCE original by each cutoff. At T−6h, Stage14 attempts within about 11:57–11:59:58; a late write cannot be made “on time” with a fabricated timestamp. The *four-hour segment* means how long the airport sampling window is exposed, **not** that all flights are only sampled three times per day.

### What the 31-day geometry really counts

Twenty-six four-hour parent sampling days = **104 active hours**. Three days made of two active 2-hour pieces separated by a **1-hour NO-COLLECTION gap** = **12 active hours** (six pieces). Two days of up to six hours = up to **12 active hours**. Total **31 parent batch-days, 128 maximum active hours and 26+6+2 = 34 active segments**. With **four airport slots per day**, there are 34×4=136 airport-segment opportunities; multiply by the **three horizon-source classes** gives **408 logical airport×segment×horizon planning groups**. These groups are not 408 unique flights or requests. Their physical GET count depends on the actual signed date/time range, partitioning, refreshes, availability and provider entitlement. Twenty-one ordinary days need true prospective early-selected airports; no fabricated names. The allowed site draw time **at most 72h and strictly more than 24h45m** before the first parent window means choose airports three days to a little more than one day ahead, so genuine T−24h work can be prepared.

### Why 60min refresh can cost LESS than 5min

A **refresh interval** is the time between repeat physical FIDS GETs for the same approved source group. In a four-hour period, requesting **once per 60min** gives 4 calls; **once per 30min** gives 8; **once per 15min** gives 16; **once per 10min** gives 24; **once per 5min** gives 48. MORE frequent refresh means MORE calls and unit costs. The 128h×4 airports×3 horizon plans×(60/interval) formula below was a **hypothetical upper-exposure sensitivity** with independent uniform refresh in every active hour; real T24/T6/T90 fetch times may fall on another date, and some groups may be combined or partitioned. Never turn that table into a signed paid schedule.

Example: hourly four-hour period × four airports × three horizon-source plans = **48 hypothetical physical FIDS GETs**. At a verified Tier2 cost of **2 API units each**, that's **96 REST units for FIDS only**, before POST/retries/history/diagnostics/Alerts. Even if one GET returns 50 eligible flights, the single GET still costs by endpoint tier, not 50×2. “As much as budget allows” should mean as many **useful unique eligible flights with valid PRE+POST outcomes** as possible, including balanced regions—not the highest raw row or refresh count.

### Why source policy, privacy, as-of weather, model features and “POST” matter

**AeroDataBox remains the primary flight source.** FIDS provides intended schedule/departures; a callback is a provider-pushed update, not necessarily every operating flight; POST is later outcome observation. **Source class** means which ADB *evidence type* a row came from. “Original” means the provider response was actually received and durably saved, with its arrival/commit clocks and content hash. “Normalize” means convert the response into rows, preserve operating-versus-codeshare classification and reference the genuine original. “Packet” is the reviewed task instruction derived from the true original. “Approved deterministic policy” means approved stable rules create many such instructions automatically; it is **not** itself approval to store or redistribute flight Contents beyond the real ADB agreement. Keep private material out of PUBLIC GitHub.

**NOAA METAR** is an observed *airport* weather report, not whole-route weather. Code already exists to parse METAR for the four Gate5 airports and select a timestamp-safe **one-airport** weather feature. It does NOT currently calculate origin+destination forecast+en-route weather for every sampled route, and Stage14 currently writes \`features:[]\`. Correct route weather would require verified route/waypoints, departure/ETA timing and appropriate already-issued TAF or SIGMET/forecast grid joins. Missing route weather should be NULL with provenance, not borrowed from a wrong airport. [NOAA AviationWeather data catalog](https://aviationweather.gov/data/api/) distinguishes METAR/TAF/SIGMET; [FAA guidance](https://www.faa.gov/air_traffic/publications/atpubs/fs_html/chap5_section_2.html) similarly distinguishes departure, route and destination. Don't claim client-ready ML solely because collection can run for 31 days.

**Good prediction depends on joint valid PRE+POST labels**. Schedule revisions observed in FIDS are not always physical wheels-off delays. Use cutoff-safe features, chronological splits and held-out later data. Scientific tests with 50/100/250/500 tasks are **synthetic pressure experiments** at varying load, not expected real fleet counts. \`p50/p95/p99\` describe median and slow tail latency; database connections/CPU and GitHub minutes are runtime resource metrics, not billable AeroDataBox API units.

## 2. Terminology for the research owner
- SOURCE GET: one physical billable AeroDataBox airport/time-window HTTP request. One original may contain **many** normalized records, including codeshare/ambiguous entries.
- SOURCE original: genuine saved provider response with actual available-at and expiry/rights metadata. Never infer a response existed from a future reservation.
- Operating flight: independent real operated-leg identity, not simply a marketing flight number; conditional scheduled service must stay a separate evidence tier.
- Horizon / cutoff: for native first scheduled T, C=T−24 hours, T−6 hours, or T−90 minutes. C belongs to the individual flight; source and predictive features must predate C.
- PRE task: ONE flight × ONE horizon due at its own C. Eight tasks is not eight GETs, eight airports, or eight daily flights.
- Controller: GH process that chooses/starts reviewed time-window jobs. Worker lane: one simultaneous independent restricted PG16 Stage14 transaction. Shard: a page/group of candidate tasks, not a scientific sample-selection rule.
- POST: source captured later to calculate the predeclared provider-observable label; missing POST is UNKNOWN, never event=0. Alert callback is independent source evidence, not the complete flight denominator.
- Signed packet: a specific reviewed byte-immutable instruction/permit for one task; a SHA alone is not an approving human signature or independent provider/rights evidence.
- Scientific FREEZE approves the population/target/source rights/time/budget/recovery design. Separate paid Phase6 GO activates costs. Green CI alone authorizes neither.

3. **Policy→private packet materialization**: independent approver signs **deterministic generator version, selected airport/day/population rules, legal source-Contents purpose, verified source class/native T semantics and private PK/residency policy**, so per-flight permits can be automatically verified against actual post-COMMIT originals. #555/#558/#559 functions are reused. 4. **Prearm**: one logical GH controller pre-dispatches a SMALL number of scoped horizon/UTC-window jobs well before individual due cutoffs. The exact lead is from measured GH cold-start p99 and dropped polls; jobs are NOT one-per-flight and not longer than GH 6h. For 6h segments, split into overlapping bounded subjobs rather than relying on one near-6h job. GH-only timing, no Replit cron/Cloudflare.
5. **Parallel PRE**: inside each GH job, a bounded async semaphore on independent DB connections/processes (test 1/2/4/8/16 lanes), earliest-deadline-first, each packet waits outside any SQL transaction until its OWN true DB-clock <=3min pre-C window; then calls SAME existing Stage14. A flight A waiting to become due cannot consume a write lane that would prevent B's closer cutoff; planner must separate waiting/prearmed tasks from actual active database-work slots. Never use one giant Promise.all for all flights or a globally canceling GH concurrency group.
6. **Receipts and recovery**: immutable record of eligible/due/attempt/COMMIT_ACK/POST-COMMIT_READBACK; independent read-only reconcile for uncertain flight; unrelated flights continue when DB/source safety is verified. Global breaker only for shared DB or clock outage, rights invalidation, budget breach, active STOP or credential compromise. A fresh no-row SELECT alone cannot prove prior TX cannot still COMMIT; retry requires separately approved bounded protocol, prior writer fenced, uniqueness and true remaining pre-C margin. Default no retry for same packet until proof.
7. **POST + receiver + STOP**: existing independent V0083 non-FIDS category reservation, actual POST FIDS originals, published raw-first webhook receiver, Flight Alert subscription lifecycle and owned STOP. Count missing POST as unknown, not negative. Labels cannot use estimated/plan schedule as actual wheels-off. T24 missing may be an honestly labeled partial T6/T90 if separate v2 amendment is adopted; do not discard unrelated flight records.
8. **Read-only daily QA**: dashboard of source qualified members, true PRE T24/T6/T90 snapshots, candidate/censor per reason, joint PRE+valid POST label, routes/tail/weather bitemporal features, per-flight receipts and ambiguous commits, seven UTC REST spend/credits/STOP, real running GH/PG costs and TTL deletions. Site sampling and protected day26–31 test outcomes remain frozen, never post-outcome optimized.

## 6. Queue and concurrency decisions / relax the right constraints
**Option A — existing per-flight children:** reuse as fallback only; too much GH dispatch/startup, 4/10min is artificial. **Option B — current 8 sequential:** safe manual debug fallback, not high-volume design. **Option C+ — preferred:** 2-4 GH horizon-window jobs per current due cluster if measured and a bounded async pool per job; keep source/POST/Alert as independently metered. **Option D — tiny durable PG task queue:** only after measured missed GH runs, restart, duplicate claims or long backlogs justify it; use short SKIP LOCKED claims, lease/fencing, no row locks while waiting. **Option E — one GH job per flight:** overhead; not first choice. **Option F — 31-day always-running process:** not possible within GH 6h per-job limit and conflicts GH-only source-of-truth.
**Relax/remove after independent prospective amendment + tests:** hard 8 sequential packets, 4/poll, 96 page as one scientific population limit, two-minute packet cutoff clustering, blanket flight-level failure stopping all other flights, human signatures per flight where a reviewed deterministic population policy could sign automatically, blanket missing T24 invalidating genuine later horizons, unnecessary repeated paid pilots.

Investigate trustworthy independent COMMIT timing/witness proof and test before loosening; do not relabel late/ambiguous rows or bypass original safety automatically.
