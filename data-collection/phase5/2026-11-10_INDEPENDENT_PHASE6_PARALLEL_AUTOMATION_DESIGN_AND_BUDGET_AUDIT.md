## 1. Review verdict
**Agree with the central thesis.** Four child GitHub dispatches per ten-minute poll, the 96 packet-entry shard, eight sequential packet tasks with a two-minute deadline span, and stopping unrelated valid flights on one per-flight failure are **project software restrictions** rather than intrinsic provider monthly data limits. The current eight-task Stage14 wrapper waits for EACH packet's own three-minute write window inside a sequential loop, so unrelated later packets can miss their own deadlines. Do not freeze this as the target production automation.
**Recommend benchmark-first Option C+:** a small number of GitHub-only prospective horizon-window jobs, each prearmed well before due time, loading an independently authorized SOURCE-day policy and verified private candidate packets, with a measured bounded parallel Node/PG Stage14 worker pool (test lanes 1/2/4/8/16; don't select a live concurrency without measurements). Every eligible flight/horizon has a distinct source, deadline, attempt and verified receipt. Independent local failures are quarantined and reconciled without stopping unrelated healthy lanes; systemic rights, DB, budget or STOP failures open a global circuit breaker.
**Do not rewrite** existing Stage14 serializable writer, PG16 source ledger, postcommit T24 witness, B0062 calendar/early draw, 7-category UTC budget ledger, V0083 POST ledger, or webhook receiver. Add a durable task queue / leasing TABLE only if stress + restart tests prove existing ledgers can't safely handle worker ownership. Design should be one logical controller, NOT one 31-day GH job.
**P0 beyond throughput:** Stage14 currently calls buildPreSnapshot with features: [] and scheduleVersion:null. Existing historicalFeatureStore_v3, weather as-of selector, route/model-support audit and ML input audit exist but Stage14 does not yet populate a predictive vector. A real as-of feature-join/manifest needs integration before claiming 31-day PRE capture creates trainable prediction examples. Preserve missing optional features; no feature joins using information first available after individual cutoff.

## 2. Terminology for the research owner
- SOURCE GET: one physical billable AeroDataBox airport/time-window HTTP request. One original may contain **many** normalized records, including codeshare/ambiguous entries.
- SOURCE original: genuine saved provider response with actual available-at and expiry/rights metadata. Never infer a response existed from a future reservation.
- Operating flight: independent real operated-leg identity, not simply a marketing flight number; conditional scheduled service must stay a separate evidence tier.
- Horizon / cutoff: for native first scheduled T, C=T−24 hours, T−6 hours, or T−90 minutes. C belongs to the individual flight; source and predictive features must predate C.
- PRE task: ONE flight × ONE horizon due at its own C. Eight tasks is not eight GETs, eight airports, or eight daily flights.
- Controller: GH process that chooses/starts reviewed time-window jobs. Worker lane: one simultaneous independent restricted PG16 Stage14 transaction. Shard: a page/group of candidate tasks, not a scientific sample-selection rule.
- POST: source captured later to calculate the predeclared provider-observable label; missing POST is UNKNOWN, never event=0. Alert callback is independent source evidence, not the complete flight denominator.
- Signed packet: a specific reviewed byte-immutable instruction/permit for one task; a SHA alone is not an approving human signature or independent provider/rights evidence.
- Scientific FREEZE approves the population/target/source rights/time/budget/recovery design. Separate paid Phase6 GO activates costs. Green CI alone authorizes neither.

## 4. 31 batch-day geometry and cost-envelope arithmetic
The prescribed shape is 26×4h + 3×(2h active+gap+2h active) + 2×up-to6h = **at most 128 active segment hours**; 34 child active segments, four airport slots, three PRE horizons => 408 airport-segment-horizon TARGET GROUPS, not 408 guaranteed REST calls. Sites on the 21 ordinary adaptive days are not drawn until legitimately prospective early selection. These are batch-days, not necessarily 31 consecutive calendar days.
Hypothetical uniform FIDS refresh across maximum 128 active hours × 4 airports × 3 horizons, ONE Tier-2 GET (2 API units) every interval, excluding boundaries, partitions, before/after-active prearm, source validation, POST/outcome, retry, diagnosis and Alerts:
| Refresh interval | Hypothetical physical FIDS GETs | Tier-2 units total | Units / 31 batch-days average |
|:--|--:|--:|--:|
| 60 min | 1,536 | 3,072 | 99 |
| 30 min | 3,072 | 6,144 | 198 |
| 15 min | 6,144 | 12,288 | 396 |
| 10 min | 9,216 | 18,432 | 595 |
| 5 min | 18,432 | 36,864 | 1,189 |
These are NOT actual feasible endpoint partition counts, due-time coverage, a selected refresh policy, a fixed service day, or a paid budget. They reveal that the source cadence, not SQL worker count, determines FIDS spend. Existing PG daily UTC/project cap max 1,900 units is project-owned, not a universal vendor limit; actual physical UTC day plus monthly billing cycle/cap must pass **all seven categories**. A 31-batch-day study might cross one or more vendor billing renewals. Historical grandfathered 60k API-unit entitlement and **separate 50k project-cycle ceiling** are account evidence, NOT remaining quota or permission to spend.
Alert SENDs are a separate **1 credit per flight item sent, including billable failed retries**. The planned 1,900-credit cap per budget-day is a MAXIMUM, not funded expected consumption: 31×1,900 = **58,900 credits** if that exposure were actually used. Historic Nov 7 balance 1,830 and protected floor 1,000 imply only **830 old opening credits** available before additional explicitly authorized refills; actual current balance must be checked. If one hypothetical cycle tried to spend 58,900 alerts starting from 1,830 and keeping 1,000 floor, it would need **58,070 refilled units**, >50k project cycle even BEFORE any REST. Across multiple billing cycles arithmetic differs; NEVER assume 1,900/day can all be afforded. For comparison 200/day over 31 days would be 6,200 send credits (5,370 extra refills from that dated opening/floor if all else unchanged), plus actual FIDS/POST units.
**No exact future usable physical flight count can be inferred from quota.** Unique true operated legs, matched POST outcomes, source permissions, source timing and actual traffic must be counted. Historical bulk FIDS record count is not unique operated flight count; refreshing one source many times produces repeated source observations, not independent training flights. Report source-reported, normalized members, unique positive physical identities, PRE per horizon, joint PRE+valid POST, known route, label prevalence and optional as-of feature availability, all by airport/tier/day.

## 5. Proposed automatic owner DAG (not a new SQL data path)
1. **Before each future sample day**: freeze 31-day date/treatment/region/UTC shape rule, five paired crossover candidates and prospective ordinary site-draw rule; early draw four airports with inclusion probabilities >24h45m and ≤72h prior to earliest parent window, and freeze source and seven-category REST plus Alert physical budget reservations with independent rights approval. Existing B0062/Stage21-22/V0082-V0083.
2. **SOURCE**: GH schedule discovers due day/airport/horizon requests; durable idempotent paid reservation BEFORE physical GET; one original saved once, normalized flight members; record true provider arrival and PG time, TTL, codeshare/conditional status and all missingness; POST source later separately.
3. **Policy→private packet materialization**: independent approver signs **deterministic generator version, selected airport/day/population rules, legal source-Contents purpose, verified source class/native T semantics and private PK/residency policy**, so per-flight permits can be automatically verified against actual post-COMMIT originals. #555/#558/#559 functions are reused. Never interpret a SHA as independent license and do not require manual typing of every individual flight. Bounded private pages and audit complete eligible denominators, no automatic public Contents publication.
4. **Prearm**: one logical GH controller pre-dispatches a SMALL number of scoped horizon/UTC-window jobs well before individual due cutoffs. The exact lead is from measured GH cold-start p99 and dropped polls; jobs are NOT one-per-flight and not longer than GH 6h. For 6h segments, split into overlapping bounded subjobs rather than relying on one near-6h job. GH-only timing, no Replit cron/Cloudflare.
5. **Parallel PRE**: inside each GH job, a bounded async semaphore on independent DB connections/processes (test 1/2/4/8/16 lanes), earliest-deadline-first, each packet waits outside any SQL transaction until its OWN true DB-clock <=3min pre-C window; then calls SAME existing Stage14. A flight A waiting to become due cannot consume a write lane that would prevent B's closer cutoff; planner must separate waiting/prearmed tasks from actual active database-work slots. Never use one giant Promise.all for all flights or a globally canceling GH concurrency group.
6. **Receipts and recovery**: immutable record of eligible/due/attempt/COMMIT_ACK/POST-COMMIT_READBACK; independent read-only reconcile for uncertain flight; unrelated flights continue when DB/source safety is verified. Global breaker only for shared DB or clock outage, rights invalidation, budget breach, active STOP or credential compromise. A fresh no-row SELECT alone cannot prove prior TX cannot still COMMIT; retry requires separately approved bounded protocol, prior writer fenced, uniqueness and true remaining pre-C margin. Default no retry for same packet until proof.
7. **POST + receiver + STOP**: existing independent V0083 non-FIDS category reservation, actual POST FIDS originals, published raw-first webhook receiver, Flight Alert subscription lifecycle and owned STOP. Count missing POST as unknown, not negative. Labels cannot use estimated/plan schedule as actual wheels-off. T24 missing may be an honestly labeled partial T6/T90 if separate v2 amendment is adopted; do not discard unrelated flight records.
8. **Read-only daily QA**: dashboard of source qualified members, true PRE T24/T6/T90 snapshots, candidate/censor per reason, joint PRE+valid POST label, routes/tail/weather bitemporal features, per-flight receipts and ambiguous commits, seven UTC REST spend/credits/STOP, real running GH/PG costs and TTL deletions. Site sampling and protected day26–31 test outcomes remain frozen, never post-outcome optimized.

## 6. Queue and concurrency decisions / relax the right constraints
**Option A — existing per-flight children:** reuse as fallback only; too much GH dispatch/startup, 4/10min is artificial. **Option B — current 8 sequential:** safe manual debug fallback, not high-volume design. **Option C+ — preferred:** 2-4 GH horizon-window jobs per current due cluster if measured and a bounded async pool per job; keep source/POST/Alert as independently metered. **Option D — tiny durable PG task queue:** only after measured missed GH runs, restart, duplicate claims or long backlogs justify it; use short SKIP LOCKED claims, lease/fencing, no row locks while waiting. **Option E — one GH job per flight:** overhead; not first choice. **Option F — 31-day always-running process:** not possible within GH 6h per-job limit and conflicts GH-only source-of-truth.
**Relax/remove after independent prospective amendment + tests:** hard 8 sequential packets, 4/poll, 96 page as one scientific population limit, two-minute packet cutoff clustering, blanket flight-level failure stopping all other flights, human signatures per flight where a reviewed deterministic population policy could sign automatically, blanket missing T24 invalidating genuine later horizons, unnecessary repeated paid pilots.
**Preserve:** original source authenticity, first selected native T, true clock and no postcutoff PRE, actual flight vs conditional service stratum, immutable site inclusion probabilities, held-out labels, source-use/TTL, seven UTC REST budgets and Alert SEND/refill/STOP, production ACL, never silent after-uncertain-COMMIT duplicates.
**Audit possible overrestriction separately:** current Stage14 demands post-COMMIT readback clock < own C; a truly committed pre-C row with delayed readback might be quarantined despite an on-time DB write. Investigate trustworthy independent COMMIT timing/witness proof and test before loosening; do not relabel late/ambiguous rows or bypass original safety automatically.
**Important SQL uniqueness check:** source ledger unique query, physical attempt and original binding are distinct and already enforce many invariants. Snapshot conflict key includes flight_instance_id/horizon/cutoff and advisory lock is flight|horizon, but review actual DB indexes and competing version behavior with disposable PG16. Don't add a second duplicate PRE writer.

With 250 tasks, eight lanes ideal 156.25sec, but p99 connection/lock penalties can destroy this. These are NOT measured service rates or approval. Do not impose an untested absolute percent completeness gate; compare across the exact same denominator and protect against concentration in easiest HUB.
