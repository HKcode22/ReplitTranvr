# Phase 5 — real feasibility problem: 4 T−6h/T−90m child requests per 10-minute GH poll

**November 10, 2026 — pure offline capacity review, IN REVIEW.** The actual default-OFF multi-flight signed PRE controller merged in [PR #552](https://github.com/HKcode22/ReplitTranvr/pull/552) uses **maximum four new PRE child `workflow_dispatch` requests each ten-minute cron pass**. That is a proven code-level *dispatch ceiling*, not an actual observed flight-processing throughput. A Phase5 scientific FREEZE should not assume that all thousands of FIDS population members can have 2 complete later PRE snapshots merely because the GitHub guard unit tests pass.

## Precise optimistic arithmetic

With every scheduled poll available and zero startup/API/network delays, the upper bound is **4 × 6 = 24 later PRE child attempts per hour** and **24 × 24 = 576 later PRE child attempts per day**. If *each flight* needs both T−6h and T−90m and no flights are excluded, this supports at most 288 distinct two-horizon flights/day even in this best-case ideal. This counts GitHub dispatch *attempt slots*, **NOT actual committed PRE snapshots**. Real missed/late cron jobs, 115-minute worker resource use, GH concurrency, source TTL, serializable transaction/retry safety, member identity review, legal use and budget can only reduce coverage. The source 1..96 *queries* per day are not one-to-one with actual normalized flight members and must not be treated as 96 flights.

## Implementation and evidence from this branch

`server/lib/disruption/phase5LaterPreGithubDispatchCapacityEnvelope_v39.ts` is a pure deterministic optimistic earliest-deadline-first simulator from independently supplied future signed **flight/horizon**, selected native T and **actual separately verifiable packet registration time**, and an explicitly supplied assumed successful GitHub 10-minute (or slower) poll grid. It refuses >4 per poll, faster-than-ten-minute tick assumptions, duplicate same flight/horizon, malformed SHA/identities, future polls after declared model end. Each flight is classified as an *optimistic GH slot*, a packet signed too late, a capacity-censored request, or a still-unassessed future window. No provider, SQL, GitHub dispatch, worker, legal release or PRE write. It does not decide whether T−24h exists: missing-T24 can still be a separately approved scientific tier under existing v2, but not implicitly granted by capacity.

`tests/phase5_later_pre_github_dispatch_capacity_envelope_v39.test.ts` is an offline synthetic stress suite: **100 distinct flight horizons sharing a single T−6h cutoff** and all signed early have only **32 theoretical slots** across eight valid 10-minute polls in the 90-to-15-minute pre-cutoff window; the other 68 are correctly labeled capacity shortfall. Fewer ticks reduce throughput, registered-after-window packets remain late/censored (never backfilled), unfinished future windows remain pending rather than falsely invalidated. Separate same-flight T6 and T90 are counted as two child requests; earliest cutoff gets priority without using outcomes or route value. These are mathematical fixtures, **not an observation of 100 AeroDataBox flights**.
