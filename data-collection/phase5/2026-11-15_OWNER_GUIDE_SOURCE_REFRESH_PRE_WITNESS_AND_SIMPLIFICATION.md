# Owner engineering guide — SOURCE timing, PRE packet, T24 witness, scope simplification

November 15, 2026 UTC. Explanatory checkpoint, not a new release gate or independent approval.

## What actually runs

SOURCE is an airport FIDS departure GET to AeroDataBox, not a paid request per flight. Refresh = repeat the same airport/partition/horizon population acquisition every 15 minutes during the bounded cutoff acquisition schedule, not all airports continuously. Store each valid original plus normalized rows; overlapping observations may provide new data but must not replace a frozen flight/horizon PRE. Native T = provider-reported scheduled departure, with physical operating-leg and schedule semantic review; not an estimated time or actual takeoff. PRE packet = a scoped, reviewed instruction with source query and response identifiers, immutable flight identity, T, horizon, cutoff and feature config. The existing writer validates the actual database records and cutoff, then commits its PRE. The packet is not a prediction or another provider request.

For illustration, scheduled departure 12:00 UTC Nov22 -> T24 Nov21 12:00; T6 Nov22 06:00; T90 Nov22 10:30. PRE must commit before its own frozen cutoff. T24 comparison, T6 conditional primary gate-out delay, T90 update, separate airborne ETA. Actual gate-out label remains separate from runway takeoff, schedule and estimated gate-out.

## 6,144 and latency geometry

Actual first seed calendar proposal has 31 parent days, 34 active segments totaling 128h; 4 airport slots, 3 horizons, 4 nominal refreshes/hour, 128*4*3*4=6144 base planned one-GET templates = 12,288 assumed API units. Includes base and split partitions, excludes retry or other REST categories. A template is a configuration/scheduled acquisition, not a completed call or flight. An ordinary 4h parent has 16 refresh slots per airport/horizon -> 192 GETs -> 384 units. One GET may yield many rows.

The #742 modeled cutoff TIME geometry starts from scheduled GET + 120s slip + 180s acquisition/persistence + 900s candidate review lead (no extra audit delay). 10:00 scheduled, 10:02 start illustrative, 10:05 available, earliest modeled eligible cutoff 10:20. 30m nominal age limit -> 10:20..10:30; next request at 10:15 gives 10:35..10:45. Recurring 5-minute gaps -> 10/15 = 66.67%. 45m limit -> 10:20..10:45, overlapping next 10:35..11:00; 100% in steady state but actual finite 36 partitions x four slots x initial 300 seconds = 43,200 uncovered of 1,843,200 airport-slot-cutoff-seconds/horizon -> 97.65625%. These are NOT flight coverage or model accuracy. No measured latency is implied. Model conservatively uses nominal scheduled request timestamp for upper age boundary; actual Stage14 checks cutoff minus persisted source availability, which is not the same age reference. The 15m lead is a current candidate preparation allowance, not a measured processing requirement or 15m PRE commit window. Actual Stage14 commit has its distinct DB-clock 180s admission and before-cutoff proof.

The new aggregate telemetry reuses already-verified original and candidate records, no extra SQL query, schema, provider call or gate. It reports reservation-to-retrieval, retrieval-to-persist, persist-to-availability, availability-to-binding, binding-to-audit-transaction-clock, planned-to-reservation/availability where signed schedule exists, and actual age/lead quantiles among otherwise eligible or lead-only-censored candidate observations. Reservation is not HTTP start, retrieval clocks do not establish provider network latency alone. Audit transaction clock is not audit completion or whole worker latency. Counts compare existing 15m lead with illustrative 10m/5m, without changing admission or recovering missing data. Per-response observations can repeat flights; do not sum as unique flight yield. Actual p95/p99 planning must use sufficient representative real measurements, not the test fixtures. No additional phase or hard gate for diagnostics.

## Why T24 evidence and private transport?

T24 writer commits PRE; separately restricted witness checks original committed row before cutoff. Receipt contains private flight identity, source and snapshot references, and before-cutoff readback time. It is not another AeroDataBox request, another flight, or proof of actual gate-out. Public GitHub workflow output is not appropriate storage for private flight records. #741 log redaction, #744 reads already-existing PRE and witness from DB, distinguishes actual absent T24 from partial or missing receipt. #745 V0101 extends the existing V0094 table, no new table/role, with exact signed custody record; all six checks passed, real synthetic PG16 test verifies private write/readback, tamper/expiry/no-replay. V0101 NOT installed; not yet connected to actual T24 worker or routing. Retaining receipt is useful when paired comparison exists, not a prerequisite to all primary T6/T90. A legitimately missing T24 uses the existing separately approved standalone later route, never fabricated T24, never treating a partially committed T24 as absent.

Daily index = append-only routing inventory of approved SOURCE/PRE/POST packets. Signature checks bytes were approved under the pinned signer policy. Delegated signing = protected key and preapproved strict policy, not human review of every index change. No duplicate new signing mechanism solely for bookkeeping.
