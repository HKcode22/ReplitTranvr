**State:** CODE IN REVIEW on feature branch — no live Phase6 source, no flight PRE, no provider spend, no rights certification, no Phase5 scientific FREEZE. This is a future production **mechanism**, not an activated 31-day collection or external approval.

## Why we implemented it

Earlier main PR #551 (merged `c6c61b661431a091857cdcd588d444f50b9870e6`, 6/6 exact-head CI success) connected existing single signed T6/T90 future PRE to one default-OFF GitHub 10-minute cron. However the GitHub variable `P5_LATER_PRE_FROZEN_PACKET_FILE` and exact packet SHA secret were global: scaling to many flights would require manually rotating a secret for every distinct flight and horizon. That is *not* a real unattended 31-day study. We reuse the actual signed SOURCE per-day registry (PR #540/541) instead of starting a different airport sample/calendar, and reuse the original PRE PG16 custody and Stage14 serializable writer without copying SQL migrations.

## Independent release security / scientific invariants

- Source capture must FIRST exist as an actual original bound to a real SOURCE day/query and FIDS physical member. Neither calendar, packet nor GH SHA can turn unknown conditional services into real operating legs, physical wheels-off, or licensed retention.
- Every PRE still passes the original **real** serializable Stage14 source/member/witness/as-of/own cutoff/post-COMMIT checks. A missed T24 can be truthfully marked missing and prospective T6/T90 captured only under a separately approved protocol SHA; no simulated T24 and no late backfill. POST can use at least one true PRE, not necessarily all three.
- Bounded at most 96 signed future packet entries **per independently approved shard**, max four GH child dispatch requests per due poll. **Not** a complete multi-shard automatic generator and not proof throughput is sufficient for the full 31-day volume. Missing flights, source expiry, rejected packets, missed cutoff and unknown GH response have explicit censor/HOLD; do not invalidate unrelated successfully captured PRE. GH run history is a non-atomic duplicate suppressor, Stage14 DB is the authority; a 204 GH ACK is not PRE evidence.
- Existing multiquery SOURCE day registry is reused; the later-PRE shard's `sourceDayRegistrySha256` must equal its independent external SHA secret and all entry `queryDigestSha256` must exist in source registry. One SOURCE batch may correspond to more than one flight; no manufactured per-flight original response.
- Keep `P5_LATER_PRE_BATCH_AUTO_DISPATCH_ENABLED` unset/false until real external signed A/C/D release and independent actual production DB/allowed-use review. **Do not enable Phase6 or spend a provider GET because CI is green.**
- The existing optional single-flight v1 scheduled job remains available but **must not run concurrently** with new batch mode. Same child workflow's deterministic run-name allows duplicate-run suppression across manual and batch attempts.
- Production REST REVIEW/RESERVE logins V0083 already truly commissioned and independently verified in [run #42831851454](https://github.com/HKcode22/ReplitTranvr/actions/runs/42831851454). Never repeat commissioner, migrations or earlier pilot.
