# November 15 Pacific — bounded GitHub handoff canary (no provider or database)

## Why this is material
Real schedule run creation history on Nov14–15 contains multi-hour gaps in nominal 5/10-minute controllers (see #784). This is an actual timing risk, not a new scientific requirement. Phase4 already used a GitHub-hosted prearmed worker after a missed WSSS cron (see [Oct31 checkpoint](../phase4/2026-10-31_WSSS_T6_GITHUB_SCHEDULER_MISS_T90_PUSH_PREARM_RECOVERY.md)); Phase5 V0080 retains signed exact prearm and PostgreSQL cutoff. Do not replace either. A healthy scheduler heartbeat is not a deadline guarantee.

GitHub's current [GITHUB_TOKEN documentation](https://docs.github.com/en/actions/concepts/security/github_token) explicitly permits workflow_dispatch-triggered runs, and [troubleshooting](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows) documents schedule delays and dropped jobs. Production source dispatcher already uses the REST dispatch response with returned run ID. Reuse that exact acknowledgement pattern.

## Implemented test path
Extend existing `.github/workflows/phase5-autonomous-clock-canary-no-provider.yml` with separate manual BOUNDED_HANDOFF mode. Default OBSERVE and existing six-slot cron unchanged. A single exact reviewed main root starts an at-most-three-run chain: hop 0 -> hop 1 -> terminal hop 2, one POST per nonterminal run; shared absolute deadline ≤30 minutes. Each hop validates its actual main run identity/title, previous chain run (when present), pinned current main and deadline, and refuses re-runs or ambiguous POST receipt. A successful acknowledgement is not child execution proof. Each job prints only own and acknowledged next run IDs and clocks; no DB URL, provider token or flight content. One isolated job uses built-in GitHub token actions:write; all ordinary clock jobs remain actions:read. No persistent PAT, environment credential, production activation or new schedule. This finite test is NOT a production rolling controller or proof of 31-day autonomy.
