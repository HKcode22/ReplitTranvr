## 1. The shortest possible explanation

We are **not yet collecting the final machine-learning dataset**.

Right now we are in **Phase 2G / Gate 2 / Stage 1**. Stage 1 is a controlled airport-selection experiment. We have a frozen list of 12 candidate HUB airports. For each valid candidate, the plan wants the same two-hour live AeroDataBox Flight Alert measurement under the same weekday/time-class rules.

The purpose is to learn which airports give useful live data for the later experiment.

During each valid probe we measure things such as:

- how many rows arrive per hour;
- how many distinct physical flights we observe per Alert credit;
- how many useful aircraft/tail-chain links we obtain per credit;
- how stable the delivery rate is across complete 15-minute buckets;
- how much flight-identity ambiguity remains;
- whether provider spend, cleanup, and our internal accounting reconcile.

Only after Stage 1 has enough valid candidate results do we score/rank candidates under the already-frozen formula. Stage 2 later performs longer four-hour confirmations. The final ML collection comes later.

## 3. Why did this seem to work before but fail now?

There are two separate ideas that can look like the same thing.

### 3.1 The older webhook system was simpler operationally

The older mental model was roughly:

```text
AeroDataBox
   ↓
public webhook/server
   ↓
PostgreSQL
   ↓
rows stay there
```

If that server was deployed or continuously hosted, closing the browser did not necessarily stop it.

The current Phase-2G path is intentionally stricter:

```text
exact Git commit
+ exact human AUTH
+ exact runtime/budget-day binding
+ exact callback health
+ safe raw storage
+ temporary runtime bookkeeping
+ provider/account reconciliation
+ cleanup proof
        ↓
only then paid Stage-1 execution
```

That extra strictness is deliberate. It prevents us from spending credits or calling a run scientifically valid when the code/runtime/account state is not exactly the state we approved.

The downside is that infrastructure problems that the older system might have tolerated or hidden are now exposed as hard failures.

### 3.2 The current Gate-2 callback is tied to a Replit development workspace

For current Gate-2 work, the callback is the Replit `.replit.dev` managed application. That process can survive a shell/browser disconnect while the workspace stays alive, but a complete Replit workspace/container restart can kill the process.

That is a real operational weakness we discovered live. The scientific plan did not fail; the hosting/runtime continuity around the live probe failed.

## 4. Is this happening because we are using a production database instead of a development database?

**Not primarily.**

The production database itself is not the reason WSSS, MMUN, or P2G05 failed.

What the real/long-lived database did do was expose a migration-replay defect that an empty or fresh development database could easily hide.

The problem was:

```text
old migration 0022
    tried to recreate an old tier_source constraint
        ↓
current database already contains newer f.8 frame rows
using traffic_reference / missing_reference
        ↓
old constraint is incompatible with those modern rows
        ↓
boot replay failed
```

Later migrations 0028 and 0057 had already replaced that old rule, but every app boot replays migrations from the beginning. Migration 0022 was trying to resurrect the obsolete constraint **before** the later migration could remove/replace it again.

We fixed 0022 so that if the modern 0057 contract already exists, it does not recreate the obsolete rule.

After the repair:

- the real boot-migration path successfully applied 0002 through 0057;
- the database verifier passed 123/123 checks;
- a genuine managed Replit restart successfully booted on the repaired code.

So the useful lesson is:

> A fresh development database can hide upgrade/replay bugs because it has little historical state. A long-lived real database can expose them. That does not mean "production PostgreSQL is bad"; it means migration code must work both on a fresh database and on an already-upgraded database.

## 7. What is a callback?

A callback/webhook is simply a public URL that AeroDataBox can send notifications to.

For example, conceptually:

```text
AeroDataBox detects flight update
        ↓
POSTs notification to our URL
        ↓
our Replit server receives it
        ↓
we store/process it
```

For the current prepaid probe path, the URL also contains a runtime-session identity so incoming deliveries belong to one exact probe session.

If the Replit server disappears, AeroDataBox has nowhere to deliver the webhook. That is why callback availability matters during a live probe.

---

## 8. What is "runtime"?

"Runtime" means the software/process state that exists **while the program is actually running**.

Examples:

- the `npm run dev` server process;
- the Git SHA that process started from;
- the active probe session;
- the current heartbeat;
- the current callback URL;
- temporary live bookkeeping rows.

Source code sitting on disk is not the same thing as runtime.

That is why we saw:

```text
git checkout HEAD = new commit
running server     = old commit
```

The files had changed, but the already-running Node process had not restarted. Our health check caught that mismatch.

---

## 9. What is a Git SHA and why do we care?

A Git SHA is the exact identifier for one version of the repository.

We use it as a safety seal.

If we approve a paid run on SHA A, but the running server is actually SHA B, we stop.

That prevents:

```text
approve one version
→ unknowingly execute another version
→ spend credits
→ later be unable to prove what code produced the result
```

---

## 10. What is a migration?

A database migration is a versioned change to database structure/rules.

Examples:

- create a table;
- add a column;
- add/remove a CHECK constraint;
- add an index.

"Migration replay" means running the ordered migration chain again to prove it is safe and idempotent on the current database.

It should be possible to start the application again without an old migration breaking a database that has already advanced to newer migrations.

## 11. Why are there temporary UNLOGGED tables?

During a live paid probe we need temporary operational bookkeeping:

```text
which runtime session is active?
which delivery arrived?
which normalized item belongs to it?
which provider subscription is bound?
```

Those rows are not the final scientific result.

The temporary tables are:

- `clean.prepaid_probe_session_runtime`
- `clean.prepaid_probe_delivery_runtime`
- `clean.prepaid_probe_item_runtime`

Successful cleanup should leave them empty.

Therefore:

```text
sessions   0
deliveries 0
items      0
```

after completion/cleanup is **good**.

The durable scientific result is saved separately in `clean.adb_anchor_probe`.

## 12. What does "reconciliation" mean?

Reconciliation asks whether different views of the same operation agree.

For a successful probe we do not only ask:

> Did the script finish?

We ask things like:

- did external provider/account movement agree with our internal accounting?
- did the expected owned subscription exist?
- was it cleaned up?
- did the result bind to the exact runtime session?
- did temporary state disappear?
- are there unexpected foreign billable subscriptions?
- does durable evidence say `MATCH`?

OMAA has `reconciliation_status=MATCH`.

WSSS/MMUN are `UNRESOLVED` because their abnormal infrastructure exits did not produce the complete valid scientific/reconciliation path.

## 13. Baseline — what does that mean here?

"Baseline" is overloaded, which caused confusion.

In plain language, a baseline is simply **a known reference state used for comparison**.

Examples in this project:

### Engineering baseline

A known code/database state that passes tests. We compare later changes against it.

### Zero-credit soak baseline

Before deliberately causing a restart/outage, we run the synthetic callback repeatedly while everything is healthy. That establishes:

> "When nothing is intentionally broken, this path repeatedly passes."

Then we deliberately stop/restart the managed callback and check whether the soak detects the outage and later recognizes recovery.

### Provider planning baseline

The Plan also uses "baseline" for some provider entitlement/account assumptions. That is unrelated to the callback soak.

A baseline does **not** mean the final ML model.

## 14. Calibration — what does that mean here?

There are two different concepts that previously shared the word "calibration."

### 14.1 Stage-1 anchor yield

The binding Plan renamed the old term **"calibration"** to **"yield-reference normalization"** because "calibration" was confusing.

For Stage 1:

- WSSS is the primary yield reference;
- OMAA is the pre-frozen fallback if WSSS is invalid/fails the capacity rule;
- candidate yield components are standardized relative to the permitted reference;
- yield contributes only 20% of the total anchor score.

This is **not model calibration**.

### 14.2 ML model calibration

Much later, after collection/modeling, probability calibration means things such as reliability/ECE/Brier behavior.

That is a different concept and is not what we are doing in Phase 2G.

So when discussing current Stage 1, prefer:

> **yield-reference normalization**

rather than "calibration."

## 15. What is the "synthetic callback test"?

Synthetic means **we generate a fake test notification ourselves** instead of asking AeroDataBox to create a paid subscription and send a real flight alert.

The current verifier:

1. confirms the public callback is healthy;
2. sends a request using a wrong secret and requires a 404;
3. creates a temporary local prepaid runtime session;
4. sends one fake flight notification through the real public callback;
5. confirms Object Storage + temporary DB rows exist;
6. deletes/cleans them;
7. proves no live blob/runtime rows remain;
8. confirms no incident opened.

It explicitly reports:

```text
providerCalled=false
providerSubscriptionCreated=false
alertCreditsSpent=0
```

This tests our infrastructure without consuming a candidate airport or Alert credits.

## 16. What is the zero-credit soak test?

"Soak" means repeat a system check for a longer period instead of testing it once.

The new weekend harness repeatedly runs the already-proven synthetic callback preparation.

Each cycle must prove:

```text
WORKSPACE_CALLBACK_PREP=PASS
AERODATABOX_PROVIDER_CALLED=false
ALERT_CREDITS_SPENT=0
```

It records:

- cycle count;
- pass count;
- failure count;
- consecutive failures;
- maximum consecutive failures;
- whether it later recovered after a failure.

The planned sequence is:

```text
healthy baseline cycles
        ↓
deliberately stop managed callback
        ↓
soak should record failures
        ↓
restart managed callback
        ↓
soak should return to PASS
        ↓
prove outage detection + recovery
```

This is **engineering validation**, not scientific Stage-1 data.

It uses no WSSS/MMUN/LKPR result and no Alert credits.

Important limitation: if the **entire Replit container** is destroyed, the soak process itself also dies because it lives inside that same container. A same-workspace test cannot prove independent recovery from total host destruction.

## 17. Why not run real WSSS/MMUN/LKPR on Saturday or Sunday?

The frozen Stage-1 protocol requires a matched **weekday class (Mon–Fri)** and the frozen 12:00 UTC time class with permitted start roughly 11:00–13:00 UTC.

Running a real candidate on Saturday/Sunday would change the experimental condition.

Therefore the weekend is useful for:

- callback tests;
- restart tests;
- migration replay;
- zero-credit soak;
- failure/recovery simulation;
- documentation;
- rerun-policy resolution.

It should **not** be used to generate a real Stage-1 candidate result.

## 18. The unresolved WSSS/MMUN rerun question

This is important and must not be hidden.

Scientifically, WSSS and MMUN were interrupted by verified infrastructure problems rather than poor airport performance. It is reasonable to want a clean identical-protocol rerun so infrastructure failure does not bias candidate selection.

However, the current Stage-1 owner code treats these statuses as terminal:

```text
completed
failed
abandoned
```

That means the current code would skip WSSS/MMUN and choose the first later non-terminal primary, presently LKPR.

The binding Plan also freezes the sequential candidate protocol and does not currently contain a fully explicit "infrastructure-invalid one rerun" rule.

Therefore we must **not silently rerun WSSS/MMUN and must not silently skip the scientific issue either**.

Before the next paid weekday run, we need one formal decision consistent with the Plan:

- preserve existing failures in history either way;
- if an infrastructure-invalid rerun exception is adopted, define it before another candidate outcome is observed and apply it symmetrically to any candidate meeting the same objective failure criteria;
- otherwise continue under the current terminal-status owner behavior.

This is a documentation/protocol-reconciliation task, not permission to rewrite history.


The goal of the weekend work is to stop discovering these engineering defects using paid scientific windows.
